# 05. 実装の順序

## 基本方針: 縦の串を先に通す

**1 つのスライスを DB → API → 画面まで貫通させてから次に行く。**
「まず全部のテーブルを作る」「まず API を全部書く」と層ごとに横に作らない。

理由は 2 つ。層をまたぐ問題（型の受け渡し、CORS、ビルド順、コンテナの設定）は**貫通させて初めて出る**。
そして、動くものが常に手元にあると、次に何が必要かの判断が具体的になる。

---

## Step 0 — 疎通（完了）

環境構築とドキュメント。`/api/health` と、それを叩く 2 つの SPA の骨組みまで。

`docker compose up` で 3 つの開発サーバが立ち、両 SPA に API の応答が表示されれば完了。

---

## Step 1 — スキンの形式を確定させる（完了）

**最初にここをやる。** 形式が後から変わると、保存済みのデータの移行が発生するため。

1. `packages/sprite` の `parseSkin()` と `toRenderable()` を実装
2. 単体テストを書く。特に **「矩形結合の結果を展開し直すと元と 1 ドットも違わない」**
3. `@mba/sprite-react` の `<Sprite>` が、手書きのサンプルスキンを描けることを確認

画面も DB もまだ要らない。純粋関数だけなので、テストで完結する。

実装時の判断は [docs/02-sprite-format.md](02-sprite-format.md) §実装に追記した。

---

## Step 2 — スキンを保存して表示する（最初の縦の串）（完了）

```
エディタ（最小） → POST /api/skins → SQLite → GET /api/skins/:id → <Sprite> で表示
```

1. `packages/db` に `skins` テーブルを足して `db:generate`
2. `POST /api/skins`（`parseSkin()` を通し、`toRenderable()` の結果も一緒に保存）
3. `GET /api/skins/:id`
4. `apps/web` に最小のエディタ（CSS グリッドのセルを塗るだけ）と保存ボタン

**この時点でエディタは完成品でなくてよい。** 1 パーツ・1 コマ・数色で十分。
串が通っていることの確認が目的で、道具としての使い勝手は Step 6 で上げる。

実装時の判断は [docs/04-api-design.md](04-api-design.md) §実装 と
[docs/03-data-model.md](03-data-model.md) §マイグレーション に追記した。

---

## Step 3 — マップを表示して歩く（完了）

1. `maps` テーブルと `GET /api/maps/:id`
2. `@mba/core` の `step()` を実装（純粋・テストあり）
3. `apps/web` にマップ画面。タイルは CSS グリッドで描く
4. `saves` テーブルと `PUT /api/save`。リロードしても位置が残ること

実装時の判断は [docs/01-architecture.md](01-architecture.md) §データの流れ（移動とセーブを例に）、
[docs/03-data-model.md](03-data-model.md) §マップ、[docs/04-api-design.md](04-api-design.md) §実装 に追記した。

---

## Step 4 — バトル（完了）

1. `@mba/core` の `calcDamage()`（乱数は引数で受け取る。中で `Math.random()` を呼ばない）
2. `species` / `moves` / `owned_monsters` テーブル
3. `POST /api/battles` と `POST /api/battles/:id/turn`。**乱数はサーバで引く**
4. バトル画面

**勝敗の判定をクライアントに置かない。** 学習用でも、ここを最初からサーバに置いておくと
「信用できる境界はどこか」という感覚が身につく。

実装時の判断は [docs/01-architecture.md](01-architecture.md) §データの流れ（バトルを例に）、
[docs/03-data-model.md](03-data-model.md) §モンスターとバトル、[docs/04-api-design.md](04-api-design.md) §実装 に追記した。
テーブルは上の 3 つに加えて `species_moves`・`map_encounters`・`battles` を足している。

---

## Step 5 — 管理画面（完了）

1. `/api/admin/species` と `/api/admin/maps`
2. `apps/admin` に一覧と編集フォーム
3. モンスターの見た目は `@mba/sprite-react` でプレビュー（プレイヤー側と同じコンポーネント）

管理画面を後回しにするのは、**編集する対象が固まってからの方が作りやすい**ため。
先に作ると、スキーマが変わるたびにフォームを直すことになる。

実装時の判断は [docs/04-api-design.md](04-api-design.md) §実装 に追記した。やっていないことは次のとおり。

- **retire**（提示から外す）。消す手段も外す手段もまだ無い（docs/03 §削除しない）
- **技の追加・更新。** 一覧を読めるだけ。種族のフォームは既にある技から選ぶ
- **マップの大きさの変更。** API は受け付けるが、画面には無い。新しいマップは 16×12 で始まる
- **マップ間の移動。** マップは増やせるが、プレイヤーが開始マップから出る手段がまだ無い

## Step 6 — エディタを道具として仕上げる（完了）

Step 2 の最小エディタを、実際に描ける道具にする。

- パーツの切り替えと、他パーツの半透明表示（位置合わせ）
- パレット。**「色を選ぶ／色を足す」と「色を作り直す」を UI で分ける**
  （後者はその色を使っている全パーツに波及するため）
- コマの追加と再生
- 着せ替えプレビュー

実装時の判断は [docs/02-sprite-format.md](02-sprite-format.md) §エディタ に追記した。上の 4 つに加えて、
保存したスキンをエディタで開き直せるようにした（`GET /api/skins/:id/source`）。描き直せない道具は道具にならないため。

やっていないことは次のとおり。

- **元に戻す（undo）。** 「このパーツを消す」も色の作り直しも、やり直しはきかない
- **色を消す。** パレットは足すことと作り直すことしかできない（理由は docs/02）
- **描きかけの保存。** 別の画面に移っても絵は残るが、リロードすると消える
- **ほかのスキンのパーツとの組み合わせ。** プレビューで試せるのは、パーツを外すことと色を変えることまで。
  「自分の髪に他人の服」は見た目のレシピ（`appearances`）の仕事で、まだ無い

## Step 7 — 本番相当の 1 コンテナ確認（完了）

```sh
docker build --target prod -t monster-battle-app .
docker run -p 3000:3000 -v mba-data:/app/data monster-battle-app
```

`/` と `/admin` の両方が開き、`/api` が同じポートで応答すること。
開発時（Vite のプロキシ）と本番（Hono の静的配信）でパスの解決が変わる部分が、ここで初めて表に出る。

**パスの解決は壊れなかった。** 開発時から本番と同じ形にしてあったため。管理画面の `base` は開発時も `/admin/` で、
両 SPA は API を相対パス（`/api/...`）でしか呼ばない。どこが開発と本番で違い、どう揃えてあるかは
[docs/01-architecture.md](01-architecture.md) §開発と本番で変わるところ に表にした。

**表に出たのは、パスではない 3 つ。**

- **ビルドコンテキストに開発用の pnpm ストアが入っていた**（約 300 MB）。dev コンテナはバインドマウントの都合で
  ストアをリポジトリの直下に作る。`.dockerignore` に無かったので、`COPY . .` がビルド用の段に運び、
  そこから本番イメージまで届くところだった。`.dockerignore` に足した（`.env` も一緒に）
- **`docker stop` に 10 秒かかり、強制終了されていた**（終了コード 137）。コンテナの中ではこのプロセスが PID 1 で、
  PID 1 にはシグナルの既定の動作が無い。`index.ts` に終了処理を書いた。今は 0.1 秒で、終了コード 0 で止まる
- **dev コンテナが動いていると、ポート 3000 がぶつかる。** 上のコマンドは dev を止めてから実行するか、
  `-p 3300:3000` のように公開するポートを変える

**確かめたこと。** `/`・`/admin`・`/admin/` がそれぞれの SPA を返し、各ページが参照するアセットと `/api` が
同じポートで応答すること。コンテナを作り直しても、ボリュームに保存したスキンと位置が残ること。
マップ・バトル・エディタ・管理画面のブラウザ操作が、開発時と同じ手順で通ること。

## ここから先（Step 8〜12）

Step 0〜7 で、最初に描いた構成は一通り動いた。ここから先は、設計にあって作っていないものを埋めることと、
作ったものを壊さずに育てられるようにすること。

順序の理由は 1 つで、**先に確認を自動にする**。Step 7 までは、画面の確認を毎回手でやり直してきた。
この先の Step はどれも既にある画面に手を入れるので、手で確かめ直す範囲が Step ごとに広がっていく。

## Step 8 — 画面の確認をテストにして、CI で回す（完了）

```
push ─┬─> 型・lint・整形・単体テスト ───────────────────────────────┬─> 結果
      └─> 本番イメージをビルド ──> そのコンテナに対して画面のテスト ─┘
```

1. マップ・バトル・エディタ・管理画面の流れを、Playwright のテストとしてリポジトリに置く
2. テストの相手は開発サーバではなく、**本番イメージのコンテナ**にする
3. イメージのビルドから画面のテストまでを、手元で 1 コマンドで回せるようにする
4. 同じコマンドを GitHub Actions で、push と PR のたびに回す

**相手を本番イメージにする理由。** 開発サーバで通ることは、配るものが動くことを意味しない。
Step 7 で出た不具合は、どれも開発サーバでは起きなかった。確かめたいのは配るものの方。

**開発用のコンテナは変えない。** ブラウザ入りの環境は別のコンテナにする。テストの道具とその依存を、
アプリの依存グラフと開発用イメージに入れないため。

**CI と手元で、同じコマンドを使う。** CI にしか無い手順があると、CI でだけ落ちる理由を手元で調べられない。

**コマンドは 2 つになった。** 組み立てと使い方、落ちたときの調べ方は [docs/06-testing.md](06-testing.md) に書いた。

```sh
docker build --target check .                                             # 型・lint・整形・単体テスト（425 件）
docker compose -f docker-compose.e2e.yml up --build --exit-code-from e2e  # 本番イメージに対する画面のテスト（34 件）
```

Step 7 までに手で確かめていた流れ（マップ・バトル・エディタ・管理画面と、1 ポートでの配信）は、すべて画面のテストになった。
GitHub Actions のワークフロー（`.github/workflows/ci.yml`）は、チェックアウトしてこの 2 つを走らせるだけ。

**書いてみて分かったこと。**

- **通っていたテストのうち 2 本は、何も守っていなかった。** 守っているはずのコードを壊しても通る。どちらも書き直し、
  ほかのテストも、壊して落ちることを確かめた（docs/06 §書いたテストは、壊して確かめる）
- **コンテナの中のブラウザから、別のコンテナをサービス名で呼ぶやり方は 2 回失敗した。** `app` という名前は HSTS のせいで開けず、
  ほかの名前ではリクエストがたまに 5 秒止まる。テストをサーバのネットワークに同居させ、数字の住所で呼ぶことにした
  （docs/06 §コンテナ同士の住所）
- **tmpfs は root の持ち物としてマウントされる。** 非 root で動くアプリが DB のファイルを作れなかった。
  `docker-compose.e2e.yml` で所有者を指定している
- **Dockerfile の段を 1 つ増やした。** 依存を入れ終えたところ（`deps`）から、検査（`check`）とビルド（`builder`）が分かれる。
  lint と整形はツリー全体を歩くので、ビルドの成果物ができる前に見る

**やっていないこと。** ビルドのキャッシュの工夫、CI からの成果物の持ち出し、Chromium 以外のブラウザ、見た目の比較。
理由は docs/06 §今は入れていないもの。

**確かめたこと。** 2 つのコマンドが、クローンし直したリポジトリで、キャッシュ無し・`CI=true` で通ること。
画面のテストが、同じサーバに続けて 3 回走らせても、コンテナの CPU を 0.5 個に絞っても通ること。
`check` が、型・lint・整形・単体テストのどれを壊しても、その検査の段で落ちること。
ワークフローは書き方を actionlint で見た。ワークフローそのものは、手元では走らせられない。

## Step 9 — 見た目のレシピ（完了）

docs/03 にあって、まだ無い最後のテーブル。「どのスキンを・どの色で・どのパーツを差し替えて着るか」を
ユーザーごとの数十バイトとして持つ。スキンを数値にした判断（docs/02）が、ここで最後までつながる。

```
[きがえの画面]  着るスキン・差し替えるパーツ・変える色を選ぶ
    │  レシピ（スキンの id と色）。絵は送らない
    ▼
[API]  parseAppearance() で検証 ──> 参照先が実在するか ──> appearances を上書き
    │
    ▼
[マップ画面]  レシピを取得 ──> 名前の挙がったスキンを取得 ──> composeAppearance() で 1 体に組む ──> <Sprite>
```

縦の串は 3 本。この順に通す。

1. **スキンを着る。** `appearances` テーブル、`GET` / `PUT /api/appearance`、選ぶための `GET /api/skins`。
   マップ上の自分を、着ているスキンで描く（今はただの丸）
2. **色を変える。** レシピに「この色を、この色に」を足す。エディタの「色を試す」と同じ仕組み（CSS 変数の上書き）を、
   保存できる選択にする
3. **パーツを差し替える。** レシピに「このスロットは、別のスキンのものを使う」を足す

レシピの形は次のとおり。`PUT` はこれ全体を送る。

```json
{ "skinId": "…", "parts": { "hair": "…" }, "colours": [{ "id": "hair", "hex": "#cc3344" }] }
```

**着手する前に決めたこと。**

- **レシピもユーザー入力。** 書けるのは識別子と色だけ。色の id は CSS 変数の名前に、色は CSS の値になるので、
  スキンのパレットと同じパターン（docs/02）で縛る。境界は `@mba/sprite` の `parseAppearance()` 1 つ。
  そのあとで、スキンが実在するか・色の id がその見た目のパレットにあるかを DB で見る
- **保存するのはレシピだけ。** 組み上げた絵は保存しない（docs/03「DB は識別子と数値を持つ。絵は持たない」）。
  組むのはブラウザで、`@mba/sprite` の純粋関数 `composeAppearance()` がやる
- **色の id は、スキンをまたいで通じる「役割」。** `hair` を赤にすると、どのスキンから来たパーツでも、
  `hair` で塗ったところが赤くなる。CSS 変数がそう働くので、それをそのまま仕様にする
- **`GET /api/me` ではなく `GET /api/appearance`。** docs/04 の表では `/api/me` に見た目を載せる予定だった。
  `PUT` する先と同じ場所から `GET` できる方が素直で、`/api/save` もそうなっている。
  ユーザー情報を使う画面はまだ無いので、`/api/me` は作らない
- **レシピが無いときは、既定のスキンを着ていることにする。** `GET /api/save` がセーブ無しでも開始地点を返すのと同じで、
  「新しいプレイヤーはどう見えるか」をクライアントに書かせない。既定のスキンは、モンスターの絵と同じく種まきする
- **着られるのは、存在するスキン全部。** 自分で描いたもの、最初からあるもの、モンスターの絵。
  スキンの規格（docs/02）が全スキンで共通なので、どれを組み合わせても位置が合う
- **`PUT` は置き換え。** レシピ全体を送る。足す・消すの差分は送らない

**やらないこと。** モンスターの色違い（所持モンスターにレシピを持たせること）。ほかのプレイヤーの見た目を見ること（1 人用）。
参照先のスキンが retire されていたときの扱い（retire は Step 10。そのとき取得層に足す）。

**書いてみて決まったこと。** 形式の側の判断は [docs/02-sprite-format.md](02-sprite-format.md) §見た目のレシピ、
テーブルは [docs/03-data-model.md](03-data-model.md) §見た目、API は [docs/04-api-design.md](04-api-design.md) に書いた。
着手前の計画から変わったこと、書くまで見えていなかったことは次のとおり。

- **色は、id をキーにしたオブジェクトではなく、エントリの並びにした。** 計画では `{ "hair": "#cc3344" }` だった。
  id はユーザーが付ける名前で、`constructor` もパターンに合う。オブジェクトだと、何も設定していなくても値が返ってくる
- **「その見た目にある色」は、パレットにある色ではなく、実際に塗られている色にした。** パーツを差し替えると、
  着ているスキンのパレットにはあるのに、どこにも塗られていない色ができる。変えても何も起きない色は、レシピに書けない。
  API のテストの 1 つがまさにそういう色を送っていて、サーバに断られた。間違っていたのはテストの方だった
- **組む関数は、サーバも呼ぶ。** 描くためではなく、上の検査のため。同じ関数なので、きがえの画面が出す色の欄と、
  サーバが受け付ける色がずれない
- **最初から入っているスキンは、服の下の体まで描いてある。** パーツを差し替えたとき、差し替えた先が覆わないところが
  透けないように
- **きがえの画面は、選んだ色を覚えておき、送るときに落とす。** 髪を別のスキンのものに替えると、元の髪の色は
  レシピに書けなくなる。画面の上では残しておき、送る直前に、その見た目に無い色を除く。髪を戻せば色も戻る
- **マップの自分は、タイルを移るたびに作り直される要素。** だから見た目は親の側で 1 回だけ取る。
  1 歩ごとに取り直していないことは、テストがリクエストを数えて確かめている
- **エディタの「色を試す」も、同じ入口を通るようにした**（`<Sprite colours>`）。CSS 変数の名前を作る場所が、
  読む側（`fill`）と書く側（上書き）で 1 つのファイルに揃った

**やっていないこと。**

- **`GET /api/me`。** 使う画面が無い。スキンの一覧が「自分のものか」を返すので、画面は自分の id を知らなくてよい
- **きがえの一覧に絵を出すこと。** 選ぶのは名前から。同じ名前のスキンが 2 つあると、見分けるには選んでみるしかない
- **モンスターの色違い、ほかのプレイヤーの見た目、retire されたスキンの扱い。** 着手前に決めたとおり

**確かめたこと。** 2 つのコマンドが通ること（単体テスト 538 件、画面のテスト 44 本）。足したテストは、
守っているはずのコードを壊して、落ちることを見た。単体は `parseAppearance()`・`composeAppearance()`・`coloursOf()`、
API の検査、きがえの画面の操作を 1 つずつ壊して 36 通り、画面は [docs/06-testing.md](06-testing.md) の表の 10 通り。
開発用の DB には、マイグレーションと既定のスキンが次の起動で入ること（前からある DB でも入ることを、種まきのテストが見ている）。

## Step 10 — 管理側の残り（完了）

「削除しない」と決めた（docs/03）のに、外す手段がまだ無い。その残り半分と、技の編集。

```
[管理画面]  「外す」を押す
    │  { "retired": true }
    ▼
[API]  ほかのマスターから使われていないか ──> retired_at を立てる（行は消さない）
                                                  │
        一覧・選択肢          ◀── 出さない ───────┤
        セーブ・見た目の取得  ◀── 読むときに既定へ ─┘
```

縦の串は 4 本。この順に通す。

1. **技の追加と更新。** `POST` / `PUT /api/admin/moves` と、管理画面の「技」の画面
2. **技と種族の retire。** マスター同士の参照をどう扱うか（下の「断る」側）
3. **マップの retire。** そこにいたプレイヤーのセーブをどう扱うか（「受け止める」側の 1 つ目）
4. **スキンの retire。** 着ていたプレイヤーの見た目をどう扱うか（2 つ目）。管理画面の「スキン」の画面

外す・戻すは、4 種類とも同じ形にする。

```
PUT /api/admin/{species|moves|maps|skins}/:id/retired    { "retired": true }
```

**着手する前に決めたこと。**

- **retire は「これから出さない」であって、「持っているものを取り上げる」ではない。** 一覧や選択肢からは消える。
  すでに持っている・使っているものは、できるかぎり今までどおり動く
- **戻せる。** `retired_at` を消すだけ。行もフォールバックも読むときに決まるので、戻せば元の位置・元の見た目に戻る
- **参照は 2 種類あり、扱いを分ける。**

  | 誰からの参照か | 例 | 外そうとしたとき |
  |---|---|---|
  | ほかのマスター | マップ → 種族、種族 → 技、種族 → スキン | **断る。** 誰が使っているかを返す。直せる人（管理者）が、先にそちらを直す |
  | プレイヤーのデータ | セーブ → マップ、見た目 → スキン、所持モンスター → 種族 | **断らない。** 管理者には直せないので、取得層で受け止める |

- **生きているものは、生きているものだけを指す。** 上の「断る」を逆から言ったもの。retire 済みのものを指す
  マスターは保存できないし、retire 済みのものを指したままのマスターは戻せない
- **受け止め方は取得層に 1 箇所ずつ。** 外されたマップにいたセーブは開始地点を、外されたスキンを着ていた見た目は
  既定のスキンを返す（`loadSave()` と `loadAppearance()`）。画面は「外されたもの」を知らなくてよい。
  外された種族のモンスターは、今までどおり戦える
- **フォールバック先そのものは外せない。** 最初のマップと、既定のスキン
- **一覧は 2 通り。** 管理 API の一覧は retire 済みも印を付けて返す（戻せるように）。プレイヤー向けの一覧は返さない。
  id を知っていれば絵は取れる（`GET /api/skins/:id` は変えない）。外すのは「提示」

**やらないこと。** 物理削除。プレイヤーが自分のスキンを片付けること（外せるのは管理者だけ）。外した理由や履歴を残すこと。
まとめて外すこと。

**書いてみて決まったこと。** 何が外せて何が外せないか、外されたものがどう見えるかは
[docs/03-data-model.md](03-data-model.md) §削除しない に、ルートの形の理由は [docs/04-api-design.md](04-api-design.md) に書いた。
書くまで見えていなかったことは次のとおり。

- **マップの受け止めは、1 行も足さずに済んだ。** プレイヤーの側がマップを読む関数（`findMap()`）を
  「生きているものだけ」にしたら、`loadSave()` は変えずにそのまま開始地点を返した。Step 3 で
  「マップが見つからなければ開始地点」と取得層に書いてあったため。受け止める場所を 1 箇所にしておく、の見返り
- **見た目の受け止めが返すのは、そのまま `PUT` できるレシピ。** パーツのスキンが外されたら、そのスロットを戻すだけでなく、
  それで塗られなくなった色も落とす。落とさないと、画面が受け取ったレシピを保存し直したときに断られる
- **普段の読み取りは重くしていない。** レシピが指すスキンが着られるかどうかは、id だけの問い合わせ 1 回で分かる。
  絵を読んで組むのは、外されたものがあったときだけ
- **フォームは、retire 済みでも「いま選ばれているもの」は出す。** 出さないと、保存が断られる理由が画面から消える。
  印を付けて出し、外せるようにしておく
- **「レシピが指すスキン」を数える関数を `@mba/sprite` に移した**（`skinsNamedBy()`）。API の検査、取得層の受け止め、
  画面の 3 箇所で要るようになった。2 つ目までは重複でよかったが、3 つ目で切り出した
- **ブラウザの入力制限は、テストから見ると「送られない」という動作。** 威力に 0 を入れてサーバの `bad_power` を見る
  テストは、`min` がフォームの送信を止めるので成り立たなかった。「0 は送られなかった」を、ページが出したリクエストを
  あとから数えて確かめる形にした。「起きない」ことの確認なので、すぐには見ない（docs/06）
- **前からあるテストが 1 本、一覧の並びを当てにしていた。** マップの画面は一覧の先頭を開く。retire のテストが作るマップは
  名前の順で最初のマップより前に来るので、同じサーバに 2 回目を走らせたときにだけ落ちた。名前で選ぶように直した。
  1 回目は通るので、空の DB からの実行だけでは見つからない

**やっていないこと。**

- **外したことを、持ち主に知らせること。** スキンを外されたプレイヤーは、最初のスキンに戻っているのを見るだけ
- **一覧で、retire 済みを隠したり絞り込んだりすること。** 印が付いて、薄く出る
- **使われている数を、外す前に見せること。** 押して断られたときに、誰が使っているかが出る
- **プレイヤーによる片付け、理由や履歴、一括操作。** 着手前に決めたとおり

**確かめたこと。** 2 つのコマンドが通ること（単体テスト 621 件、画面のテスト 51 本）。足したテストは、
守っているはずのコードを壊して、落ちることを見た。単体は外す・戻すの規則、取得層、管理 API、管理画面の補助関数を
47 通り、画面は [docs/06-testing.md](06-testing.md) の表の 12 通り。画面のテストは、どれも自分で作ったものだけを
外す。最初から入っている種族や技は外さないので、ほかのテストと同じ DB で続けて走らせても通る
（続けて 3 回、CPU を 0.5 個に絞って 1 回）。

## 各ステップの完了条件

共通して、以下が通ること。CI が走らせるのと同じ 2 つ（[docs/06-testing.md](06-testing.md)）。

```sh
docker build --target check .
```

そして、**その Step で足した画面の流れを、画面のテストに足す。** 型が通ることと動くことは別。
Step 7 までは動くことを毎回手で確かめていたが、手で確かめたことは、次の Step では確かめ直されない。テストにすれば残る。
足したテストは、守っているはずのコードを壊して、落ちることを見る。
