# 04. API 設計

## ルートの分け方

```
/api/health              生存確認
/api/...                 プレイヤー向け（ゲーム API）
/api/admin/...           マスターデータ編集（管理 API）
```

**プレフィックスを分ける理由は認可を 1 箇所に集めるため。** `/api/admin/*` にミドルウェアを 1 枚かければ、
管理系の全ルートが同じ判定を通る。ルートごとに `if (isAdmin)` を書くと、追加時に書き忘れる。

## 想定エンドポイント

### ゲーム API

| メソッド | パス | 内容 |
|---|---|---|
| GET | `/api/me` | 自分のユーザー情報（未実装。使う画面ができたら足す） |
| GET | `/api/appearance` | 見た目のレシピ。選んでいなければ既定の見た目 |
| PUT | `/api/appearance` | 見た目のレシピの置き換え（着るスキン・差し替えるパーツ・変える色） |
| GET | `/api/save` | セーブデータ（現在のマップと座標） |
| PUT | `/api/save` | セーブ |
| GET | `/api/maps/:id` | マップ（タイル配列・エンカウント設定） |
| GET | `/api/monsters` | 所持モンスター一覧（未実装。使う画面ができたら足す） |
| POST | `/api/battles` | バトル開始（サーバが乱数を引く） |
| GET | `/api/battles/:id` | バトルの今の状態（画面に要る分だけ） |
| POST | `/api/battles/:id/turn` | 技を選ぶ |
| GET | `/api/skins` | スキンの一覧（着るものを選ぶため。絵は含まない） |
| GET | `/api/skins/:id` | スキン（描画用データ） |
| GET | `/api/skins/:id/source` | スキン（編集用の正本）。エディタで開き直すときだけ使う |
| POST | `/api/skins` | **エディタが作ったスキンを保存**（docs/02 の検証を通す） |

### 管理 API

| メソッド | パス | 内容 |
|---|---|---|
| GET / POST | `/api/admin/species` | モンスター種族の一覧 / 追加 |
| PUT | `/api/admin/species/:id` | モンスター種族の置き換え |
| GET / POST | `/api/admin/maps` | マップの一覧 / 追加 |
| PUT | `/api/admin/maps/:id` | マップの置き換え（出現するモンスターを含む） |
| GET / POST | `/api/admin/moves` | 技の一覧 / 追加 |
| PUT | `/api/admin/moves/:id` | 技の置き換え |
| GET | `/api/admin/skins` | スキンの一覧（絵は含まない） |
| PUT | `/api/admin/{species\|moves\|maps\|skins}/:id/retired` | retire する / 戻す（`{ "retired": true }`） |

削除は用意しない。retire で提示から外す（[docs/03](03-data-model.md) §削除しない）。管理 API の一覧は、
retire 済みのものも `retired: true` を付けて返す。

## 認証と認可

**ローカル学習用なので、本物の認証は最初から作らない。** ただし**差し替えられる形にはしておく**。

- ユーザーの識別は `getUserId(c)` のような **1 つの関数に閉じ込める**。最初はヘッダやクエリで
  ユーザーを切り替えるだけの実装でよい
- 管理者判定も同様に 1 箇所（`/api/admin/*` のミドルウェア）に置く

こうしておけば、後で本物の認証に替えるときに触るのは 2 箇所で済む。逆に、各ハンドラで
`c.req.header("x-user-id")` を直接読んで回ると、差し替えのときに全ルートを触ることになる。

**クライアントから来た `userId` を信用しない。** 学習用の簡易実装でも、
「リクエストのボディに書いてある userId でそのまま更新する」形にはしない。
更新対象は必ず `getUserId(c)` が返した値から決める。ここを緩めると、後で認証を足しても
**認可の穴だけが残る**（本物の認証を入れても、他人の ID を書けば他人のデータを触れてしまう）。

## 層の分け方

```
ハンドラ         リクエストの受け取り、認可、レスポンスの組み立て
  │  zod で検証（形が正しいか）
  ▼
@mba/core       ドメインのルール（バトル計算・移動判定）。純粋
  │
  ▼
@mba/db         永続化
```

- **zod はハンドラで、ドメインのルールは core で。** 「power は数値か」は zod、
  「HP は 0 未満にならない」は core
- **乱数はハンドラで引いて core に値として渡す。** core の中で `Math.random()` を呼ばない。
  そうしないとバトルのテストが書けない
- **スキンと見た目のレシピの検証だけは `@mba/sprite` の `parseSkin()` / `parseAppearance()`。**
  zod のスキーマを別に書かない（2 箇所に検証があると必ずズレる）

## エラーの返し方

失敗は例外ではなく値で運ぶ（`Result<T, E>`）。ハンドラで HTTP に翻訳する。

```
{ "error": { "kind": "bad_hex", "hex": "..." } }
```

`kind` を機械可読な文字列にしておくと、クライアント側で分岐でき、メッセージの日本語化も
クライアントに寄せられる。ステータスコードは、検証エラー 400 / 認可 403 / 不在 404 に素直に対応させる。

## 実装

縦の串を通すたびに決まったこと。コードは `apps/api/src/`。

### 書いてみて決まったこと

**アプリの組み立てと起動を分けた。** `app.ts` の `createApp()` は依存（DB など）を引数で受け取って
Hono のアプリを返すだけで、ポートも DB ファイルも開かない。環境変数を読んで listen するのは `index.ts` だけ。
こうしておくと、テストはインメモリの SQLite を渡して `app.request()` を直接呼べる。
サーバを立てずに、本物のマイグレーションの上でハンドラを確かめられる。

**サイズの上限は 2 つあり、役割が違う。**

| どこで | 何を守るか | 超えたとき |
|---|---|---|
| `bodyLimit`（ルートの手前） | プロセスのメモリ。読み込む前に断る | 413 `body_too_large` |
| `parseSkin()` の `maxBytes` | 保存されるデータの大きさ | 400 `too_large` |

`parseSkin()` の上限だけではサーバを守れない。あれが走る時点で、ボディはもう全部メモリに載っている。

**保存するのはリクエストのボディではなく、`parseSkin()` が組み直した値。** ハンドラは検証に通った後、
元のボディに二度と触らない。`source` には組み直した `Skin` を、`renderable` にはそこから作った描画用データを入れる。
ボディに `ownerId` や未知のプロパティが紛れていても、保存に届く経路が無い。

**所有者は `getUserId(c)` が決める**（`auth.ts`）。今は固定のローカルユーザーを返すだけだが、
ハンドラからの呼び方は本物の認証を入れた後と同じになる。`owner_id` は `users.id` を参照するので、
起動時に `ensureLocalUser()` でそのユーザーの行を用意している。

**`GET /api/skins/:id` は、保存してある JSON 文字列をそのまま返す。** パースも再シリアライズもしない。
描画用データを書き込み時に作っておいたこと（docs/01）の見返りで、読み取りは主キーで 1 行引いて流すだけになる。
返すのは `RenderableSkin` そのもので、外側を包むオブジェクトは付けていない。型が `@mba/sprite` に既にあるので、
API とクライアントで同じ形を二重に定義せずに済む。

**`GET /api/skins/:id/source` は、もう片方の列をそのまま返す。** 正本（`parseSkin()` が組み直した `Skin`）で、
エディタが続きを描くのに要る。描くだけの画面は呼ばない。受け取った側で矩形結合をやり直すことになり、
書き込み時に 1 回で済ませた意味が無くなるため。
返ってきたものをそのまま `POST /api/skins` に送れば、新しいスキンとして保存できる（上書きの API は無い）。

**`POST /api/skins` は 201 と `{ id }` を返し、`Location` ヘッダに取得先を入れる。** 描画用データは返さない。
クライアントは改めて GET する。保存した直後の画面もリロード後の画面も、同じ経路（DB から出てきたもの）を
描くことになるので、「保存できたように見えるが実は入っていない」が起きない。

**JSON として読めないボディは 400 `bad_json`。** `c.req.json()` は例外を投げるので、ハンドラの入口で
`Result` に変換している。`parseSkin()` の `malformed`（JSON だがスキンの形でない）とは別の `kind` にしてある。

**形は zod、規則は core、の最初の実例が `PUT /api/save`。** zod が見るのは「`x` は整数か」まで。
「その座標に立てるか」は `@mba/core` の `canStandOn()` が決める。zod のスキーマは core の型（`SaveData`）で
型付けしてあるので、core の型が求めるフィールドがスキーマに欠けたり、型が食い違ったりするとコンパイルが通らない。

**サーバが見るのは「そこに立てるか」だけで、「そこまで歩いて来たか」は見ない。** ブラウザは `step()` で
1 歩ずつ動くが、サーバに届くのは結果の位置だけなので、歩けるタイルなら離れた場所でも保存できる。
今は位置に守るほどの価値が無い（1 人用で、位置から得をするものが無い）のでこうしている。
バトルを作った後も、この線は動かしていない（理由は下の「位置の検査の線引きは Step 3 のまま」）。
引き直すのは、保存がマップをまたぐとき（Step 11）と、勝つと増えるものができるとき（Step 12）。
**線を引いた場所を書き残しておく**のが目的。

**`GET /api/save` はセーブが無くても 200 で、開始地点を返す。** 「新しいゲームはどこから始まるか」を
知っているのはサーバだけにしたいので、クライアントに 404 の扱いを書かせない。GET なので行は作らない。
保存された位置が今のマップで立てない場所になっていた場合（マップを描き直した後など）も、同じく開始地点を返す。
docs/03 の「取得層でフォールバックさせる」の最初の実例で、画面側は「立てない位置」を考えなくてよくなる。

**HTTP の入口の処理は `http.ts` に 1 回だけ書く。** JSON の読み取り（`readJson`）、ボディの上限
（`jsonBodyLimit`）、zod による形の検査（`parseShape`）。ライブラリが例外を投げる場所はここで `Result` に
変わるので、ハンドラは `try` を書かない。`parseShape` が返すのはスキーマの出力なので、
スキーマに無いフィールドはそこで消える。

**乱数の出どころは `createApp` の依存として受け取る**（`random`）。ハンドラはそこから引いて、
`@mba/core` の関数に数として渡す。`Math.random` の名前が出てくるのは `index.ts` の 1 箇所だけ。
テストは数列を渡すので、誰が出るか・どれだけ効くか・勝つか負けるかを決め打ちで確かめられる。

**バトルでブラウザが決めるのは「どの技を出すか」だけ。** `POST /api/battles/:id/turn` のボディは
技の id とターン数で、HP も勝敗も受け取らない（送られても zod が捨てる）。状態は DB から読み、
`playTurn()` に通し、DB に書き戻す。返すのは `viewBattle()` が選んだ項目だけで、
攻撃・防御の値や相手の技は応答に入らない。

**ターン数を一緒に送らせて、同じリクエストの重複を見分ける。** POST は繰り返して安全ではないが、
二度押しやタイムアウト後の再送で実際には繰り返される。「これは 3 ターン目への入力」と書かせておけば、
2 通目は「もう済んだターンへの入力」と分かるので、`stale_turn` で断れる。画面側はそのときサーバの状態を取り直す。

**状態を読んでから書くまでの間に `await` を置かない。** ボディを読み終えた後は、読む・進める・書くが
同期的に続く。Node は 1 本のスレッドでハンドラを回すので、その間に別のリクエストは割り込めない。
同じ状態から 2 ターンが進むことは無い。プロセスを複数にしたら成り立たなくなる前提なので、ここに書いておく。

**バトルは、サーバが覚えている位置が草むらのときだけ始まる。** 位置はリクエストから受け取らず、
保存済みのセーブから読む。画面側は、最後の 1 歩が保存されるまで「調べる」ボタンを押せなくしている。
誰が出るかは `map_encounters` の重みと、サーバが引いた乱数で決まる。

**位置の検査の線引きは Step 3 のまま**（立てるかは見る、歩いて来たかは見ない）。位置を偽って草むらに
いることにしても、できるのはバトルを始めることだけで、バトルに勝っても今は何も得ないため。
経験値や持ち物のような「勝つと増えるもの」を作るときが、引き直すとき。

**他人のバトルは 404。** 403 にすると「その id のバトルは存在する」と教えることになる。
持ち主でない人から見れば、存在しないのと同じに見えるのが正しい。

**管理 API の認可は、ルーターの入口に 1 回だけ付ける**（`routes/admin.ts`）。管理系のルートは全部 1 つの
Hono インスタンスの中にあり、その先頭に `requireAdmin` がある。ルートごとに書かないので、
後から足したルートが検査を素通りすることが無い。テストは、定義していないパスにも 403 が返ることを見ている。
403 はボディを読む前に返る。

**「誰か」と「してよいか」を分けた。** 誰かは今までどおり `getUserId(c)` が答える。してよいかは
そのユーザーについての事実で、`users.is_admin` に持つ。本物の認証を入れたとき変わるのは前者だけ。
ローカルユーザーは自分の手元でこのアプリを動かしている本人なので、起動時に管理者にしている。

**検査は 3 段で、前が通ったときだけ次に進む。** 形（zod。数値か、配列か、タイルの名前か）、
規則（`@mba/core` の `checkSpecies()` / `checkMap()`。能力値は 1 以上、開始位置は立てるタイル）、
参照先（DB。そのスキン・技・種族は存在するか）。参照先は外部キーでも弾かれるが、あちらは例外になる。
先に聞いておけば「そのスキンは無い」を 400 として返せる。

**id はサーバが決める。** POST のボディに id を書いても使わない。PUT は置き換えで、無い id には
404 を返す（作らない）。id を配るのが POST だけなので、「PUT で好きな id の行を作る」経路が無い。

**種族と技、マップと出現は、1 つのトランザクションでまとめて置き換える。** 編集する人にとっては
1 つのものなので、種族の行だけ新しくて技は前のまま、という中間の状態を作らない。足すのではなく
置き換えなので、フォームでチェックを外した技はその種族から消える。

**編集がゲーム側にどう届くか。** 進行中のバトルには届かない（始まった時点の値を写して持っているため）。
次に始まるバトルから新しい値になる。マップを描き直してプレイヤーの足元を水にしたら、そのセーブは
次に読まれたとき開始地点に戻る（上の `GET /api/save` のフォールバック）。どちらも前の Step で
決めたことが、管理画面ができて初めて実際に効く場面。

**見た目は `/api/save` と同じ形にした**（`routes/appearance.ts`）。パスに id が無く、誰のものかは `getUserId(c)` が決める。
`GET` は選んでいなくても 200 で、既定の見た目を返す。`PUT` はレシピ全体の置き換えで、差分は受け取らない。
最初の表では `GET /api/me` に見た目を載せる予定だったが、`PUT` する先と同じ場所から `GET` できる方が素直なので変えた。

**レシピの検査も 3 段。ただし 1 段目と 2 段目は 1 つの関数。** 形と規則は `parseAppearance()` がまとめて見る
（[docs/02](02-sprite-format.md) §見た目のレシピ）。スキンと同じで、CSS に流れる文字列の検証を
2 箇所に書かないため。3 段目は DB が要るもので、名前の挙がったスキンが実在するか、変える色がその見た目に
本当にあるか。後者は、スキンを取ってきて `composeAppearance()` で組み、`coloursOf()` に聞く。
ブラウザが描くときに使うのと同じ関数なので、「この見た目にある色」の意味が両側でずれない。

**保存するのは `parseAppearance()` が組み直した値で、返すのもそれ。** ボディに `userId` や未知のプロパティが
紛れていても、保存にも応答にも届かない。着ているスキンと同じスキンを指すパーツは、落としてから保存する。
同じ見た目が 2 通りの書き方で保存されることが無い。

**スキンの一覧は、誰のものかを「自分のか、そうでないか」に落として返す**（`GET /api/skins` の `mine`）。
一覧は全員に同じものが返るが、ほかのユーザーの id は応答に入らない。画面が自分の id を知っている必要も無くなるので、
`/api/me` を作らずに済んでいる。管理 API の一覧（`/api/admin/skins`）は `ownerId` をそのまま返す。

**技は、検査が 2 段で済む。** 形（zod）と規則（`@mba/core` の `checkMove()`）。技は何も指さないので、
参照先を確かめる 3 段目が無い。威力を変えても、進行中のバトルには届かない（種族の編集と同じ理由）。

**外す・戻すは、状態を `PUT` する。** `PUT …/retired` に `{ "retired": true }`。`/retire` と `/restore` のような
動詞のルートにしなかったのは、ボディが「どうなっているべきか」を言う形だと、同じ要求を何度送っても同じになり、
戻すのが同じ要求の値違いで済むため。すでにその状態なら何も変えずに 200 を返す（retire した時刻も動かさない）。
`DELETE` にもしなかった。消していないので。

**4 種類とも同じルートの形で、規則は 1 つのファイルにある**（`retirement.ts`）。何が外せて何が外せないかは
[docs/03](03-data-model.md) §削除しない。ハンドラは、そこが返した値を HTTP に翻訳するだけ。

**編集と retire は別の要求。** `PUT /api/admin/moves/:id` で名前や威力を置き換えても、retire の状態は変わらない。
フォームの保存が、外したものをうっかり戻すことが無い。

**「無い」と「外されている」は、管理 API では別の `kind`**（`unknown_move` と `retired_move`）。
管理者にとっては、直し方が違う（作るのか、戻すのか）。ゲーム API は区別しない。外されたスキンをレシピに書くと
`unknown_skin` が返る。プレイヤーから見れば、外されたものは無いのと同じ。

### エラーの一覧（スキン）

| ステータス | `kind` | いつ |
|---|---|---|
| 400 | `bad_json` | ボディが JSON でない |
| 400 | `SkinError` の各 `kind` | `parseSkin()` が拒否した（docs/02） |
| 404 | `not_found` | その id のスキンが無い |
| 413 | `body_too_large` | ボディが上限を超えた |

### エラーの一覧（見た目）

| ステータス | `kind` | いつ |
|---|---|---|
| 400 | `bad_json` | ボディが JSON でない |
| 400 | `malformed` | 形が違う（`at` にその場所。規格に無いスロットも含む） |
| 400 | `bad_palette_id` / `bad_hex` | 色の id・色がパターンに合わない（docs/02） |
| 400 | `duplicate_palette_id` / `too_many` | 同じ id が 2 回ある / 色が多すぎる |
| 400 | `unknown_skin` | 着るスキン、またはパーツの元のスキンが無い、または retire されている（`skinId` にどれか） |
| 400 | `unknown_colour` | その見た目のどこにも使われていない色の id（`id` にどれか） |
| 413 | `body_too_large` | ボディが上限を超えた |

### エラーの一覧（マップとセーブ）

| ステータス | `kind` | いつ |
|---|---|---|
| 400 | `bad_json` | ボディが JSON でない |
| 400 | `malformed` | 形が違う（`at` にその場所。例: `$.position.x`） |
| 400 | `unknown_map` | `mapId` のマップが無い、または retire されている |
| 400 | `cannot_stand` | マップの外、または歩けないタイル |
