# 04. API 設計

## ルートの分け方

```
/api/health              生存確認
/api/...                 プレイヤー向け（ゲーム API）
/api/admin/...           マスターデータ編集（管理 API）
```

**プレフィックスを分ける理由は認可を 1 箇所に集めるため。** `/api/admin/*` にミドルウェアを 1 枚かければ、
管理系の全ルートが同じ判定を通る。ルートごとに `if (isAdmin)` を書くと、追加時に書き忘れる。

## 想定エンドポイント

### ゲーム API

| メソッド | パス | 内容 |
|---|---|---|
| GET | `/api/me` | 自分のユーザー情報・見た目のレシピ |
| GET | `/api/save` | セーブデータ（現在のマップと座標） |
| PUT | `/api/save` | セーブ |
| GET | `/api/maps/:id` | マップ（タイル配列・エンカウント設定） |
| GET | `/api/monsters` | 所持モンスター一覧 |
| POST | `/api/battles` | バトル開始（サーバが乱数を引く） |
| POST | `/api/battles/:id/turn` | 技を選ぶ |
| GET | `/api/skins/:id` | スキン（描画用データ） |
| POST | `/api/skins` | **エディタが作ったスキンを保存**（docs/02 の検証を通す） |
| PUT | `/api/appearance` | 装備バリアント・色の変更 |

### 管理 API

| メソッド | パス | 内容 |
|---|---|---|
| GET/POST/PUT | `/api/admin/species` | モンスター種族 |
| GET/POST/PUT | `/api/admin/maps` | マップ |
| GET/POST/PUT | `/api/admin/moves` | 技 |

削除は用意しない。retire（docs/03）で提示から外す。

## 認証と認可

**ローカル学習用なので、本物の認証は最初から作らない。** ただし**差し替えられる形にはしておく**。

- ユーザーの識別は `getUserId(c)` のような **1 つの関数に閉じ込める**。最初はヘッダやクエリで
  ユーザーを切り替えるだけの実装でよい
- 管理者判定も同様に 1 箇所（`/api/admin/*` のミドルウェア）に置く

こうしておけば、後で本物の認証に替えるときに触るのは 2 箇所で済む。逆に、各ハンドラで
`c.req.header("x-user-id")` を直接読んで回ると、差し替えのときに全ルートを触ることになる。

**クライアントから来た `userId` を信用しない。** 学習用の簡易実装でも、
「リクエストのボディに書いてある userId でそのまま更新する」形にはしない。
更新対象は必ず `getUserId(c)` が返した値から決める。ここを緩めると、後で認証を足しても
**認可の穴だけが残る**（本物の認証を入れても、他人の ID を書けば他人のデータを触れてしまう）。

## 層の分け方

```
ハンドラ         リクエストの受け取り、認可、レスポンスの組み立て
  │  zod で検証（形が正しいか）
  ▼
@mba/core       ドメインのルール（バトル計算・移動判定）。純粋
  │
  ▼
@mba/db         永続化
```

- **zod はハンドラで、ドメインのルールは core で。** 「power は数値か」は zod、
  「HP は 0 未満にならない」は core
- **乱数はハンドラで引いて core に値として渡す。** core の中で `Math.random()` を呼ばない。
  そうしないとバトルのテストが書けない
- **スキンの検証だけは `@mba/sprite` の `parseSkin()`。** zod のスキーマを別に書かない
  （2 箇所に検証があると必ずズレる）

## エラーの返し方

失敗は例外ではなく値で運ぶ（`Result<T, E>`）。ハンドラで HTTP に翻訳する。

```
{ "error": { "kind": "bad_hex", "hex": "..." } }
```

`kind` を機械可読な文字列にしておくと、クライアント側で分岐でき、メッセージの日本語化も
クライアントに寄せられる。ステータスコードは、検証エラー 400 / 認可 403 / 不在 404 に素直に対応させる。

## 実装

最初の縦の串（スキンの保存と取得）を通したときに決まったこと。コードは `apps/api/src/`。

### 書いてみて決まったこと

**アプリの組み立てと起動を分けた。** `app.ts` の `createApp()` は依存（DB など）を引数で受け取って
Hono のアプリを返すだけで、ポートも DB ファイルも開かない。環境変数を読んで listen するのは `index.ts` だけ。
こうしておくと、テストはインメモリの SQLite を渡して `app.request()` を直接呼べる。
サーバを立てずに、本物のマイグレーションの上でハンドラを確かめられる。

**サイズの上限は 2 つあり、役割が違う。**

| どこで | 何を守るか | 超えたとき |
|---|---|---|
| `bodyLimit`（ルートの手前） | プロセスのメモリ。読み込む前に断る | 413 `body_too_large` |
| `parseSkin()` の `maxBytes` | 保存されるデータの大きさ | 400 `too_large` |

`parseSkin()` の上限だけではサーバを守れない。あれが走る時点で、ボディはもう全部メモリに載っている。

**保存するのはリクエストのボディではなく、`parseSkin()` が組み直した値。** ハンドラは検証に通った後、
元のボディに二度と触らない。`source` には組み直した `Skin` を、`renderable` にはそこから作った描画用データを入れる。
ボディに `ownerId` や未知のプロパティが紛れていても、保存に届く経路が無い。

**所有者は `getUserId(c)` が決める**（`auth.ts`）。今は固定のローカルユーザーを返すだけだが、
ハンドラからの呼び方は本物の認証を入れた後と同じになる。`owner_id` は `users.id` を参照するので、
起動時に `ensureLocalUser()` でそのユーザーの行を用意している。

**`GET /api/skins/:id` は、保存してある JSON 文字列をそのまま返す。** パースも再シリアライズもしない。
描画用データを書き込み時に作っておいたこと（docs/01）の見返りで、読み取りは主キーで 1 行引いて流すだけになる。
返すのは `RenderableSkin` そのもので、外側を包むオブジェクトは付けていない。型が `@mba/sprite` に既にあるので、
API とクライアントで同じ形を二重に定義せずに済む。

**`POST /api/skins` は 201 と `{ id }` を返し、`Location` ヘッダに取得先を入れる。** 描画用データは返さない。
クライアントは改めて GET する。保存した直後の画面もリロード後の画面も、同じ経路（DB から出てきたもの）を
描くことになるので、「保存できたように見えるが実は入っていない」が起きない。

**JSON として読めないボディは 400 `bad_json`。** `c.req.json()` は例外を投げるので、ハンドラの入口で
`Result` に変換している。`parseSkin()` の `malformed`（JSON だがスキンの形でない）とは別の `kind` にしてある。

### エラーの一覧（スキン）

| ステータス | `kind` | いつ |
|---|---|---|
| 400 | `bad_json` | ボディが JSON でない |
| 400 | `SkinError` の各 `kind` | `parseSkin()` が拒否した（docs/02） |
| 404 | `not_found` | その id のスキンが無い |
| 413 | `body_too_large` | ボディが上限を超えた |
