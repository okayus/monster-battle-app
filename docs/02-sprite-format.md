# 02. スキンの形式

このリポジトリで最も重要な設計判断がここにある。形式・API・セキュリティが 1 つの判断から導かれているので、
スキン周りを触る前に必ず読むこと。

## 判断: スキンはマークアップではなく数値

**ユーザーからは SVG も画像も受け取らない。** 受け取るのは専用エディタが生成した
「パレット＋パーツごとのセル列」という数値データだけ。

### なぜか

SVG は画像ではなく**実行可能な文書**で、`<script>`・`<foreignObject>`・イベント属性を仕込める。
ユーザー由来の SVG を DOM に入れれば、それは XSS そのものになる。

対処には 2 通りある。

| 方針 | 中身 | 弱点 |
|---|---|---|
| サニタイズ | 危険な要素・属性を取り除く | 除去漏れが 1 つでもあれば破られる。仕様追加のたびに再検討が要る |
| **表現できなくする** | データ形式に、危険なものを入れる場所を作らない | — |

後者を選ぶ。**配列に数値しか入らない形式なら、スクリプトは「書けない」。**
サニタイザは「危険なものを見つけて消す」防御だが、これは「危険なものが存在しえない」設計。

この判断があるので、API は**サニタイズを一切しない**。やるのは「数値が範囲内か」の検証だけ。

### 数値でない部分（＝検証の要点）

2 箇所だけ文字列が残る。ここが実質的な攻撃面なので、**完全一致のパターンで縛る**。

| 項目 | どこへ流れるか | 検証 |
|---|---|---|
| `palette[].hex` | SVG の `fill` 属性 | `/^#[0-9a-fA-F]{6}$/` に完全一致 |
| `palette[].id` | **CSS カスタムプロパティ名 `--c-<id>`** | `/^[a-z0-9-]{1,32}$/` に完全一致 |

`hex` を任意文字列にすると `url(...)` などを書けてしまう。`id` は CSS 変数名になるので、
記号を通すとスタイルシートの構文に干渉しうる。**どちらもクライアントの整形に頼らず、API で落とす。**

## データ形式

型の定義は `packages/sprite/src/index.ts` にある。要点だけ再掲する。

```ts
Skin {
  formatVersion: 1
  name: string
  palette: { id: string; hex: string }[]
  parts: { slot: PartSlot; frames: Frame[] }[]
}

Frame {
  durationMs: number
  cells: [paletteIndex, runLength][]   // ランレングス。0 = 透明、n = palette[n-1]
}
```

### なぜセルを色番号で持つのか

セルに `#5a3921` のような色そのものを入れず、**パレットの番号**を入れる。

書き出しのとき、番号は `fill="var(--c-hair, #5a3921)"` という形に写る。すると
**CSS 変数を上書きするだけで色違いが作れる**。髪の色を 10 種類用意しても、スキンのデータは 1 つのまま。
色そのものをセルに埋めていたら、色違いの数だけスキンを複製することになる。

### なぜランレングスなのか

ドット絵は平坦な塗りが多い。セルを素の数値配列で持つと、16×16×数コマで数十 KB の JSON になる。
同色の連なりを `[色番号, 長さ]` にまとめると、実データではおおむね 1 KB 未満に収まる。

**保存を始める前にこの形にしておくこと。** 後から変えると移行が要る。

### 描画用データは別に持つ

同色の隣接セルを矩形にまとめた形（`[x, y, w, h, 色番号]` の配列）を、**保存時に生成して一緒に保存する**。
読み取りのたびに結合し直さない。

- 編集用の正本 = `Skin`（ランレングス。エディタが読み書きする）
- 描画用 = `RenderableSkin`（矩形の配列。ゲーム画面が読む）

## スキン規格

パーツを重ねて 1 体にする方式は、**全パーツが同じキャンバスを共有している**から成立する。
自由なサイズ・自由なパーツ構成を許すと、他人のスキンと組み合わせた瞬間に位置が合わなくなる。

そこで**規格を固定し、それに適合するものだけ受け付ける**（`SKIN_SPEC` / `PART_SLOTS`）。

- キャンバス: **16×16 固定**
- パーツスロット: `body` / `shirt` / `pants` / `shoes` / `hair`（この順が奥→手前）
- コマ数の上限、パレット数の上限、ペイロードのバイト数上限

エディタ側もこの規格に沿わせる。「自由に描けます」にしてから規格を足すのは難しいので、最初から固定する。

## 描画はインライン SVG で

`<img src="skin.svg">` では**外側の CSS が中に届かない**。CSS 変数による色替えも、
`data-part` 単位のアニメーションも効かなくなる。

なので描画は `@mba/sprite-react` の `<Sprite>` が JSX で `<rect>` を組み立てる。
文字列を DOM に流し込む処理は一切無い（`dangerouslySetInnerHTML` を使わない）。
**これが「数値だから安全」を実際に成立させている部分**なので、ここを HTML 文字列の生成に変えないこと。

## 実装

`packages/sprite/src/index.ts`。どちらも純粋関数なので単体テストで完結する。特に `toRenderable` は
**「結合した結果を展開し直すと元のドットと 1 ドットも違わない」**という性質でテストしてある。

- `parseSkin(input: unknown): Result<Skin, SkinError>`
  唯一の信頼境界。上限・パターン・セル数の合計がキャンバスサイズの 2 乗と一致するか、まで検査する。
- `toRenderable(skin: Skin): RenderableSkin`
  ランレングスを展開し、同色の隣接セルを矩形に結合する。
- `expandFrame` / `packFrame`
  ランレングスとセル列の相互変換。エディタが読み書きする形はセル列なので、この 2 つが編集画面側の入口になる。
- `frameAt(frames, elapsedMs)`
  その時刻に映っているコマの番号。コマごとの `durationMs` を使うのはここだけ。時計は持たない。

### 書いてみて決まったこと

**パーツの並びはサーバで決める。** `parseSkin` は受け取った順ではなく `PART_SLOTS` の順で
`parts` を組み直す。配列の順序がそのまま描画順なので、クライアントに任せると
「髪を体の後ろに描くスキン」が作れてしまう。奥から手前への順序は規格の一部であって入力ではない。

**戻り値は組み直す。コピーしない。** `parseSkin` は入力をスプレッドやキャストで通さず、
検査したフィールドだけを 1 つずつ拾って新しいオブジェクトを作る。こうしておくと、
入力に紛れ込んだ未知のプロパティが保存データまで到達する経路が存在しない。

**上限を 2 つ足した**（`SKIN_SPEC`）。`name` と `durationMs` は `fill` にも
CSS 変数名にも流れないので注入面ではない。それでも、境界に立つ関数が
上限を見ていない値を素通しするのは筋が悪い。`maxNameLength` / `maxFrameDurationMs`。

**`TextEncoder` は使わない。** ペイロードのバイト数は自前で数える。このパッケージは
API・両 SPA・エディタの全部から import されるので、言語以外のもの（Node のグローバル・DOM）を
前提にしない。

## エディタ

`apps/web/src/editor/`。状態と操作は純粋関数（`model.ts`）で、画面はそれをいつ呼ぶかだけを決める。
ここに書くのは、形式の側から見て意味のある判断だけ。

**エディタのコマは、キャラクター全体で 1 列。** 形式はパーツごとに別のコマ数を許すが、描く人が考えるのは
「このキャラの 2 コマ目」なので、エディタは全パーツに全コマを持たせる。書き出すものは常に形式に適合する。
逆に、コマ数の違うスキンを開くときは、短いパーツを繰り返して書き下す（`fromSkin()`）。コマ番号で描いたときの
見た目は変わらず、繰り返しに頼らなくなるだけ。

**「色を足す」と「色を作り直す」は別の操作で、画面でも別の枠にある。** セルは色そのものではなくパレットの番号を
持つので、色を足しても描いたものは変わらない。作り直すと、その番号を使っている全パーツ・全コマのセルが
一度に変わる。それが番号で持つ理由そのものだが、うっかり起きてはいけないので、作り直す前に「どのパーツの
何マスが変わるか」を出し、ボタンを押すまで適用しない。

**色を消す操作は無い。** 番号は「パレットの何番目か」なので、途中の色を抜くと後ろの番号が全部ずれる。
全セルの書き換えになり、保存済みのスキンと番号の意味が変わる。必要になったら、消すのではなく
「使われていない色を末尾から落とす」形で足す。

**ほかのパーツを透かして見せる。** 全パーツが同じキャンバスを共有している、という規格が画面に出る場所。
袖を腕に合わせられるのは、座標が共通だから。

**着せ替えプレビューは、CSS 変数の上書きを実際に使う最初の画面。** 色を試すと、スプライトを囲む箱に
`--c-<id>` が付く。絵の側は最初から `var(--c-<id>, 描いた色)` で塗ってあるので、それだけで色が変わる。
データは 1 バイトも変わらない。パーツを外すのも同じで、描画に渡す前に抜くだけ。

**エディタの中のプレビューは、ブラウザで `toRenderable()` を走らせた結果。** 保存のときサーバが走らせるのと
同じ関数なので、プレビューと保存結果がずれる経路が無い。ただし「保存されたスキン」の表示だけは別で、
あれはサーバの応答を描く。保存できたことの証拠になるのはそちらだけ。

**再生の時計は、描画する側が持つ。** `<Sprite elapsedMs>` に経過時間を渡すと、各パーツが自分のコマの長さで
進む（`frameAt()`）。コンポーネントの中にタイマーは無いので、止めておくことも、サーバで描くこともできる。
時計が要る画面は `useElapsedMs()` を使う。動かないスキンには時計を渡さない。

**描きかけの絵は、画面の切り替えより上（`App`）に置いてある。** マップを見に行っても消えない。
リロードすると消える。
