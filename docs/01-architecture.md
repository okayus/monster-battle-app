# 01. アーキテクチャ

## 3 つの面

| 面 | 実体 | 役割 |
|---|---|---|
| プレイヤー向け SPA | `apps/web` | ゲーム画面・設定画面・スキンエディタ |
| 管理画面 SPA | `apps/admin` | モンスターやマップの追加・更新 |
| API | `apps/api` | 永続化。DB に触れる唯一のプロセス |

### なぜ管理画面を別アプリにするのか

プレイヤー向け SPA のルートとして `/admin` を足す方が手軽に見えるが、分けている。

1. **配るものが違う。** 管理画面のコードはプレイヤーのブラウザに届く必要がない。同じバンドルに入れると、
   使われないコードを全員がダウンロードすることになる。
2. **話す相手が違う。** 管理画面は `/api/admin/*` を叩く。認可の境界がアプリの境界と一致していると、
   「この画面は管理者しか開かない」という前提をコードの構造で表現できる。
3. **壊れ方が違う。** 管理画面のバグでプレイヤー側が落ちない。

本番では 1 コンテナに同居させる（下記）ので、分けたことによる運用の手間は増えない。

## ワークスペース構成と依存の向き

```
        @mba/core ──────┐
        （純粋ドメイン）  ├──> apps/api ──> @mba/db
                        │
        @mba/sprite ────┤
        （スキンの形式）  │
             │          └──> apps/web / apps/admin
             │                    ▲
             └──> @mba/sprite-react ┘
                  （React レンダラ）
```

**`@mba/sprite` と `@mba/sprite-react` を分けている理由**は 1 つで、**API が React に依存しないため**。
API はスキンを検証するが描画はしない。同じパッケージに同居させると、API のビルドに React が入り込む。
「純粋な形式の定義」と「その形式の描画方法」は別の関心事、と構造で示している。

**`@mba/core` は何も import しない。** バトルの計算やマップ移動の判定は、サーバでもブラウザでも
同じ結果でなければならない。乱数も I/O も外から値として渡し、この中では引かない。

## ポートと通信

開発時:

```
ブラウザ ──> :5173 (Vite / player) ──/api──> :3000 (Hono)
ブラウザ ──> :5174 (Vite / admin)  ──/api──> :3000 (Hono)
```

ブラウザから見た通信相手は常に 1 オリジンなので、**CORS の設定は要らない**。Vite の `server.proxy` が
`/api` だけを Hono に中継する。CORS ミドルウェアを書きたくなったら、それは構成を間違えたサイン。

本番（`--target prod`）:

```
ブラウザ ──> :3000 (Hono) ─┬─> /        apps/web/dist
                          ├─> /admin   apps/admin/dist
                          └─> /api/*   API 本体
```

1 プロセス・1 ポート。ローカル学習用なので、リバースプロキシも CDN も挟まない。

## データの流れ（スキンを例に）

```
[エディタ]  ドットを描く
    │  スキンデータ（数値）
    ▼
[API]  parseSkin() で検証  ──> 矩形結合して描画用データも作る ──> DB へ保存
    │                                                          （両方を保存）
    ▼
[ゲーム画面]  描画用データを取得 ──> <Sprite> が <rect> を組み立てる（インライン SVG）
```

**重い変換は書き込み時に 1 回だけ。** 矩形結合を読み取りのたびに走らせない。書き込みは稀で読み取りは頻繁、
という非対称を活かす。

## データの流れ（移動とセーブを例に）

```
[マップ画面]  キー入力 ──> step()（@mba/core）で、その場で移動する
    │  新しい位置（mapId と座標）
    ▼
[API]  zod で形を検査 ──> canStandOn()（@mba/core）で「そこに立てるか」を検査 ──> saves を上書き
    │
    ▼
[マップ画面]  次に開いたとき GET /api/save ──> 保存された位置から再開
```

**歩くのにサーバを待たない。** 移動の判定は `@mba/core` の純粋関数なので、ブラウザがその場で結果を出せる。
サーバは同じ関数で、送られてきた位置を検査する。「同じ規則を両側で使う」ために core を分けてある、の実例。

**保存は 1 本ずつ送る**（`apps/web/src/saver.ts`）。1 歩ごとに保存すると、リクエストが返るより速く次の 1 歩が来る。
ばらばらに投げると到着順が入れ替わりうるので、最後に保存されるのが「最後にいた場所」とは限らなくなる。
そこで、飛ばしているリクエストは常に 1 本だけにし、その間に来た位置は最新の 1 つだけ覚えておく。
途中の位置は捨ててよい。残したいのは最後の位置だけだから。

## この構成であえてやらないこと

- **認証基盤を最初から入れない。** ローカル完結の学習用なので、ユーザーの識別は差し替え可能な 1 箇所に
  閉じ込めておき（docs/04）、本物の認証は必要になってから足す。
- **状態管理ライブラリを入れない。** まず React の状態設計で組む。手に負えなくなってから検討する。
- **ルーターのライブラリを入れない。** 今いる画面は URL のハッシュだけが持ち、それを読む関数が 1 つある
  （`apps/web/src/route.ts`）。リンクはただの `<a href>` なので、戻る・進む・リロードはコード無しで動く。
- **クラウドを前提にしない。** オブジェクトストレージも CDN も使わない。ローカルの SQLite で完結させる。
