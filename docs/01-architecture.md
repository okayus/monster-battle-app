# 01. アーキテクチャ

## 3 つの面

| 面 | 実体 | 役割 |
|---|---|---|
| プレイヤー向け SPA | `apps/web` | ゲーム画面・設定画面・スキンエディタ |
| 管理画面 SPA | `apps/admin` | モンスター・技・マップの追加と更新、retire |
| API | `apps/api` | 永続化。DB に触れる唯一のプロセス |

### なぜ管理画面を別アプリにするのか

プレイヤー向け SPA のルートとして `/admin` を足す方が手軽に見えるが、分けている。

1. **配るものが違う。** 管理画面のコードはプレイヤーのブラウザに届く必要がない。同じバンドルに入れると、
   使われないコードを全員がダウンロードすることになる。
2. **話す相手が違う。** 管理画面は `/api/admin/*` を叩く。認可の境界がアプリの境界と一致していると、
   「この画面は管理者しか開かない」という前提をコードの構造で表現できる。
3. **壊れ方が違う。** 管理画面のバグでプレイヤー側が落ちない。

本番では 1 コンテナに同居させる（下記）ので、分けたことによる運用の手間は増えない。

**分けた代わりに、2 つの SPA に同じものが 2 回書いてある箇所がある。** タイルの色の表、
`fetch` を `Result` にする小さな関数、応答を待つ小さなコンポーネント（`<Loaded>`）。どれも十数行までで、
共有するにはパッケージを 1 つ増やすことになるので、今は重複を選んだ。3 つ目の利用者が出たら切り出す。スキンの描画だけは最初から共有している
（`@mba/sprite-react`）。管理画面のプレビューは、プレイヤーの画面と同じコンポーネントが、
同じエンドポイントから取ったデータを描く。近似ではなく、同じもの。

## ワークスペース構成と依存の向き

```
        @mba/core ──────┐
        （純粋ドメイン）  ├──> apps/api ──> @mba/db
                        │
        @mba/sprite ────┤
        （スキンの形式）  │
             │          └──> apps/web / apps/admin
             │                    ▲
             └──> @mba/sprite-react ┘
                  （React レンダラ）
```

**`@mba/sprite` と `@mba/sprite-react` を分けている理由**は 1 つで、**API が React に依存しないため**。
API はスキンを検証するが描画はしない。同じパッケージに同居させると、API のビルドに React が入り込む。
「純粋な形式の定義」と「その形式の描画方法」は別の関心事、と構造で示している。

**`@mba/core` は何も import しない。** バトルの計算やマップ移動の判定は、サーバでもブラウザでも
同じ結果でなければならない。乱数も I/O も外から値として渡し、この中では引かない。

## ポートと通信

開発時:

```
ブラウザ ──> :5173 (Vite / player) ──/api──> :3000 (Hono)
ブラウザ ──> :5174 (Vite / admin)  ──/api──> :3000 (Hono)
```

ブラウザから見た通信相手は常に 1 オリジンなので、**CORS の設定は要らない**。Vite の `server.proxy` が
`/api` だけを Hono に中継する。CORS ミドルウェアを書きたくなったら、それは構成を間違えたサイン。

本番（`--target prod`）:

```
ブラウザ ──> :3000 (Hono) ─┬─> /        apps/web/dist
                          ├─> /admin   apps/admin/dist
                          └─> /api/*   API 本体
```

1 プロセス・1 ポート。ローカル学習用なので、リバースプロキシも CDN も挟まない。

### 開発と本番で変わるところ

同じコードが、違う組み立てで動く。違うところは最初から揃えてあるか、起動時に吸収している。

| 何が | 開発 | 本番 | どう揃えているか |
|---|---|---|---|
| SPA を配るもの | Vite（:5173 / :5174） | Hono の静的配信（:3000） | — |
| 管理画面の場所 | `:5174/admin/` | `:3000/admin/` | `base: "/admin/"` を開発時から設定している |
| API の呼び先 | Vite が `/api` を :3000 へ中継 | 同じプロセス | SPA は相対パス `/api/...` だけを使う。絶対 URL を書かない |
| ワークスペースのパッケージ | ソースを直接読む（tsx・Vite の alias） | 各パッケージの `dist/` | `pnpm -r run build` が依存順にビルドする |
| マイグレーションの場所 | `packages/db/src` から見た `../drizzle` | `packages/db/dist` から見た `../drizzle` | どちらも同じディレクトリになる |
| 静的ファイルの場所 | — | 作業ディレクトリからの相対（`./apps/web/dist`） | イメージの `WORKDIR` が `/app` |
| 止め方 | compose の `init: true` がシグナルを中継する | プロセス自身が PID 1 | `index.ts` が SIGTERM / SIGINT を扱う |
| 乱数の出どころ | `Math.random` | `Math.random` | テストだけが数列を渡す（下の「バトルを例に」） |

**この表の「本番」の列は、画面のテストが毎回通る道になっている。** テストの相手は開発サーバではなく `prod` ステージのコンテナなので
（[docs/06-testing.md](06-testing.md)）、配る場所・パス・`dist/`・マイグレーションのどれかが本番でだけ壊れれば、そこで落ちる。
止め方だけは別で、テストは終了のしかたまでは見ていない。

**API の呼び先を相対パスにしてあることが、いちばん効いている。** SPA のコードに「開発なら :3000、本番なら同じ
オリジン」という分岐が無い。開発時は Vite が、本番では Hono が、同じ `/api` を同じオリジンで受ける。

**本番でだけ意味を持つのが、終了の扱い。** コンテナの中で直接起動されたプロセスは PID 1 になり、PID 1 には
シグナルの既定の動作が無い。何も書かなければ `docker stop` の SIGTERM は無視され、10 秒後に強制終了される。
`index.ts` は新しい接続を止め、処理中のリクエストを終わらせ、DB を閉じてから自分で終了する。

## データの流れ（スキンを例に）

```
[エディタ]  ドットを描く
    │  スキンデータ（数値）
    ▼
[API]  parseSkin() で検証  ──> 矩形結合して描画用データも作る ──> DB へ保存
    │                                                          （両方を保存）
    ▼
[ゲーム画面]  描画用データを取得 ──> <Sprite> が <rect> を組み立てる（インライン SVG）
```

**重い変換は書き込み時に 1 回だけ。** 矩形結合を読み取りのたびに走らせない。書き込みは稀で読み取りは頻繁、
という非対称を活かす。

## データの流れ（移動とセーブを例に）

```
[マップ画面]  キー入力 ──> step()（@mba/core）で、その場で移動する
    │  新しい位置（mapId と座標）
    ▼
[API]  zod で形を検査 ──> canStandOn() と canWalkTo()（@mba/core）で「立てるか・歩いて行けるか」を検査
    │                                                                        ──> saves を上書き
    │
    ▼
[マップ画面]  次に開いたとき GET /api/save ──> 保存された位置から再開
```

**歩くのにサーバを待たない。** 移動の判定は `@mba/core` の純粋関数なので、ブラウザがその場で結果を出せる。
サーバは同じ関数で、送られてきた位置を検査する。「同じ規則を両側で使う」ために core を分けてある、の実例。
サーバが確かめるのは、覚えている位置からそこまで道があるかどうか。1 歩ずつ報告させてはいない
（[docs/04](04-api-design.md) の「歩いて行ける位置だけ」）。

**保存は 1 本ずつ送る**（`apps/web/src/saver.ts`）。1 歩ごとに保存すると、リクエストが返るより速く次の 1 歩が来る。
ばらばらに投げると到着順が入れ替わりうるので、最後に保存されるのが「最後にいた場所」とは限らなくなる。
そこで、飛ばしているリクエストは常に 1 本だけにし、その間に来た位置は最新の 1 つだけ覚えておく。
途中の位置は捨ててよい。残したいのは最後の位置だけだから。

**マップを移るのは、歩くのとは逆に、待つ。**

```
[マップ画面]  出口のタイルに乗る ──> その 1 歩が保存されるのを待つ
    │  POST /api/travel（ボディ無し）
    ▼
[API]  覚えている位置に出口があるか ──> 行き先を saves に書く
    │
    ▼
[マップ画面]  開いたときと同じ経路で読み直す（GET /api/save ──> GET /api/maps/:id）
```

歩く 1 歩は、嘘をついても行けるのは同じマップの中だけなので、ブラウザがその場で決める。どのマップにいるかは
サーバが守るものなので、ブラウザは頼むだけで、サーバが移したのを見てから画面を切り替える。
切り替えた後の画面は、リロードしたときに出る画面と同じ手順で作る。ずれようがない。

## データの流れ（バトルを例に）

```
[バトル画面]  技を選ぶ
    │  技の id と、いま何ターン目か。それだけ
    ▼
[API]  DB からバトルの状態を読む ──> 乱数を引く ──> playTurn()（@mba/core）に状態と乱数を渡す
    │                                               ──> 新しい状態を DB に書く
    │  画面に要る分だけ（名前・HP・起きたこと）
    ▼
[バトル画面]  受け取った状態をそのまま描く
```

移動とは逆で、**ブラウザは何も判定しない。** ダメージの式も「倒れたか」の判定も画面側には無い。
移動は結果を偽っても得るものが無いので速さを取り、バトルは勝敗そのものが守る対象なのでサーバに置いた。
同じ `@mba/core` の純粋関数を、どちら側で呼ぶかを使い分けている。

**乱数を引くのは API、使うのは core。** core の関数は乱数を引数で受け取るだけなので、同じ入力なら必ず同じ結果になる。
API は乱数の出どころ自体を外から受け取る（`createApp` の `random`）。本番では `Math.random`、
テストでは決まった数列を渡すので、「この出目なら勝つ」「この出目なら負ける」をそのまま書ける。

## データの流れ（見た目を例に）

```
[きがえの画面]  着るスキン・差し替えるパーツ・変える色を選ぶ
    │  レシピ（スキンの id と色）。絵は送らない
    ▼
[API]  parseAppearance() で検証 ──> 名前の挙がったスキンが実在するか ──> appearances を上書き
    │  レシピ。保存してあるのはこれだけ
    ▼
[マップ画面]  レシピを取得 ──> スキンを id で取得 ──> composeAppearance() で 1 体に組む ──> <Sprite>
```

**スキンとは逆で、組み立ては読む側がやる。** スキンは、書き込み時に描画用データを作って一緒に保存した。
見た目は、保存するときに何も作らない。組んだ絵を保存すると、絵がユーザーの数だけ増えるため
（[docs/03](03-data-model.md) §見た目）。サーバが返すのはレシピと、今までどおりのスキン 1 つずつ。
読み取りの経路に新しい計算は増えていない。

**同じ純粋関数を、両側で、違う目的に使う。** `composeAppearance()` をブラウザは描くために呼び、
サーバは「このレシピが変える色は、この見た目に本当にあるか」を確かめるために呼ぶ。移動（ブラウザで判定し、
サーバで検査）とバトル（サーバだけで判定）に続く、3 つ目の使い分け。

## データの流れ（成長を例に）

```
[バトル画面]  技を選ぶ（決着がつく 1 手）
    │  技の id と、いま何ターン目か。ほかのターンと同じ
    ▼
[API]  playTurn() ──> 決着がついたら settle()（どちらも @mba/core）
    │        ──> battles・owned_monsters・（負けたら）saves を、1 つのトランザクションで書く
    │  画面に要る分だけ（HP・起きたこと・手に入れた経験値）
    ▼
[バトル画面]  受け取ったものを描く        [なかまの画面]  GET /api/monsters ──> レベルと HP
```

**書き戻すのは、決着をつけたのと同じリクエスト。** 勝ち負けを決めたターンの処理が、そのまま経験値と HP を書く。
「報酬を受け取る」ための 2 つ目のリクエストは無い。ブラウザが送るのは、最後まで技の id だけ。

**保存するのは 2 つの数で、画面に出すのはそこから導いた値。** DB にあるのは経験値と、減ったままの HP。
レベルと HP は、読むたびに `@mba/core` の関数が導く（[docs/03](03-data-model.md) §モンスターとバトル）。
スキンは書き込み時に変換して結果も保存したが、こちらは保存しない。変換が軽く、保存すると食い違う値が増えるため。

**成長の式も、バトルの判定と同じく、サーバだけが呼ぶ。** ブラウザに届くのは導いた後の値で、画面は式を知らない。
片側しか呼ばない規則も core に置くのは、I/O から切り離して、決め打ちの入力で隅まで試すため。
「同じ規則を両側で使う」だけが、core を分ける理由ではない。

## リクエストの中の 3 段

上の 5 つの流れのうち、何かを書くものは、API の中でどれも同じ 3 段を通る。

```
[ルート]  ボディを読む（await はここだけ）
    │  検査を通った入力
    ▼
[判断]  読む ──> 決める            同期の関数。渡されるのは、読むための口だけ
    │  答えと、書くことの一覧（Change）
    ▼
[commit()]  1 つのトランザクションで書く        リクエストの中で DB に書くのは、ここだけ
```

**判断は書かない。何を書くかを、値で返す。** 位置を保存する判断は「プレイヤーをここに置く」を 1 つ返す。
負けたターンの判断は「バトルをこの状態に」「モンスターをこの数に」「プレイヤーを最初の場所に」の 3 つを返す。
書くのは `commit()` で、3 つは一緒に書かれるか、1 つも書かれない。

**core が純粋なのと、同じ考えを 1 つ外側でやっている。** core は乱数も I/O も外から受け取り、同じ入力なら同じ結果を返す。
判断は DB を読むので純粋ではないが、書かない。「読んでから書くまでに割り込まれない」「全部書くか、何も書かないか」
「`GET` は行を作らない」は、ルートごとの注意ではなく、この形から出る。詳しくは [docs/04](04-api-design.md) §読む・決める・書く。

## 画面の組み立て

2 つの SPA の画面は、3 つの部品でできている。

| 部品 | 何をするか | 例 |
|---|---|---|
| `model.ts`（純粋な関数） | 画面が知っていること（状態）と、それがどう変わるか。何も取りに行かず、何も描かない | `map/model.ts` の `walk()`、`battle/model.ts` の `fight()`、`editor/model.ts`、`look/model.ts`、管理画面の `forms.ts` |
| 画面のコンポーネント | 状態を描く。キーを聞く・リクエストを送る・アドレスを変える、の 3 つだけは、ここがやる | `MapScreen.tsx`、`BattleScreen.tsx` |
| `<Loaded>` | 応答を待つ | `loaded.tsx` |

**画面の規則は、画面のテストより下の段で確かめる。** 「出口は、乗った 1 歩が保存されてから、1 歩につき 1 回だけ頼む」
「草むらは、サーバがその位置を知ってから調べられる」は、どれも状態から導く関数（`wantsExit()`・`canSearch()`）で、
ブラウザ無しで隅まで試せる。画面のテストは、部品がつながっていることを見る（[docs/06](06-testing.md)）。

**導けるものは、状態に持たない。** 「サーバがその位置を知っているか」は、覚えている位置と画面の位置が同じ
オブジェクトかどうか。「草むらにいるか」は、位置とマップから。どれも関数で、聞かれるたびに導く。
DB で `level` と `hp` の列を持たないのと同じ判断（[docs/03](03-data-model.md)）。

**待つことを、画面ごとに書かない。** 画面はリクエストを始めて、Promise を持つ。それを `<Loaded>` に渡すと、
届くまでは「読み込み中」を、届いたら中身を、読めなかったらその理由を出す。「読み込み中 / 失敗 / 済み」の状態と、
それを埋める effect と、遅れて届いた応答を捨てるための旗を、画面ごとに持つのをやめた。待ち方を知っているのは
`loaded.tsx` の 1 箇所。失敗は例外にしない。`api.ts` は今までどおり `Result` を返すので、読めなかったことは
値として届き、答えが出るはずだった場所に出る。

**リクエストを始めるのは、画面。** 画面そのもの（最初の状態として）か、イベントの中で始めて、Promise を props で
下ろす。画面が要るものは 1 箇所で、並べて頼まれる。モンスターの絵は、バトルや一覧を読んだ関数が、どのスキンかが
分かったところで取りに行き、スプライトは待つだけ。マップの自分の見た目は、マップと並べて取る。

**React の `use()` と `<Suspense>` は、使っていない。** `<Loaded>` はそれと同じ形で、Step 13 の途中までは実際に
それだった。動かして 2 つ分かり、自分で読む形に替えた（[docs/05](05-roadmap.md) Step 13）。

- **代わりの表示を 1 度出すと、React 19 は 300 ミリ秒たつまで中身を出さない。** ちらつきを抑えるための仕様で、
  数ミリ秒で答える API が相手だと、どの画面も前より 0.3 秒遅く開くようになった
- **待っている境界の中で初めて描かれるコンポーネントは、コミットされるまで状態を持たない。** React はその描画を
  やり直すことがあり、そこで始めたリクエストは、やり直すたびに始め直しになる

React の文書も、フレームワーク無しで Suspense にデータを読ませることは、まだ支えていないと言っている。
このアプリはそういうフレームワークを持たず、足すつもりも無い。

**マップを移った後は、次のマップが届いてから画面を切り替える。** 届くまで、出てきたマップが出たままになる。
「読み込み中」に戻さない。

**effect が残っているのは、画面の外と合わせるところだけ。** キーボードを聞く、位置が変わったら保存する、
出口に乗ったら頼む、きがえで選んだスキンのうち手元に無いものを取りに行く、管理画面のプレビュー。
どれも「いまの状態から決まる、外に向けた仕事」。

## この構成であえてやらないこと

- **認証基盤を最初から入れない。** ローカル完結の学習用なので、ユーザーの識別は差し替え可能な 1 箇所に
  閉じ込めておき（docs/04）、本物の認証は必要になってから足す。
- **状態管理ライブラリを入れない。** まず React の状態設計で組む。手に負えなくなってから検討する。
  画面の状態は `useReducer` と純粋な関数 1 つ、待つのは `<Loaded>` 1 つ（上の「画面の組み立て」）。
  データ取得のライブラリも入れていない。
- **ルーターのライブラリを入れない。** 今いる画面は URL のハッシュだけが持ち、それを読む関数が 1 つある
  （`apps/web/src/route.ts`）。リンクはただの `<a href>` なので、戻る・進む・リロードはコード無しで動く。
- **クラウドを前提にしない。** オブジェクトストレージも CDN も使わない。ローカルの SQLite で完結させる。
