# 03. データモデル

## 原則: DB は識別子と数値を持つ。絵は持たない

見た目は「どのスキンを着て・どのパーツを差し替えて・どの色に変えるか」という**レシピ**で表す。レシピは数十バイトで済み、
絵そのものを持つより後から効く。

- 髪の色を変えても、増えるのは 1 レコードの hex 文字列だけ。スキンは複製されない
- 「赤毛でベストを着た自分」は 1 行で表現できる

**マップも画像にしない。** タイル ID の配列として持つ。こうすると当たり判定・エンカウント判定・
経路探索が同じデータから引ける。画像にした瞬間、それらを別に持つ羽目になる。

## テーブル方針

下の表のテーブルは、すべて `packages/db/src/schema.ts` に定義してある。

### マスターデータ（管理画面が編集する）

| テーブル | 主な列 | 補足 |
|---|---|---|
| `species` | id, name, max_hp, attack, defense, skin_id, retired_at | モンスターの種族。能力値はレベル 1 のときの値。絵は `skin_id` の参照だけ |
| `moves` | id, name, power, retired_at | 技 |
| `species_moves` | species_id, move_id | 種族が覚える技 |
| `maps` | id, name, width, height, tiles, spawn_x, spawn_y, retired_at | `tiles` はタイル ID の配列（JSON を TEXT で） |
| `map_encounters` | map_id, species_id, weight | どのマップに何が出るか |
| `map_exits` | map_id, x, y, to_map_id, to_x, to_y | マップの出口。どのタイルから、どのマップのどこへ |

### ユーザーデータ

| テーブル | 主な列 | 補足 |
|---|---|---|
| `users` | id, display_name, is_admin, created_at | ローカル学習用。認証は docs/04 参照。`is_admin` は管理 API を使ってよいか |
| `saves` | user_id, map_id, x, y, updated_at | セーブデータ。1 ユーザー 1 行（`user_id` が主キー）なので、保存は上書きになる |
| `owned_monsters` | id, user_id, species_id, nickname, exp, damage, created_at | 所持モンスター。レベルと HP の列は無い（下の「モンスターとバトル」） |
| `battles` | id, user_id, monster_id, status, state, created_at, updated_at | バトル。`state` が状態のすべて（JSON）。進行中は 1 体につき 1 つ |
| `appearances` | user_id, skin_id, part_overrides, colour_overrides, updated_at | **見た目のレシピ**。数十バイト。1 ユーザー 1 行 |

### スキン

| テーブル | 主な列 | 補足 |
|---|---|---|
| `skins` | id, owner_id, name, format_version, source, renderable, created_at, retired_at | `owner_id` が null なら運営が用意したスキン |

- `source` … 編集用の正本（ランレングス）。エディタが読み書きする
- `renderable` … 描画用（矩形の配列）。保存時に生成する（docs/02）

両方を持つのは重複に見えるが、**書き込み時に 1 回変換して読み取りを軽くする**という意図的な非正規化。
`source` から `renderable` はいつでも再生成できるので、真実は `source` にある。

どちらも JSON を TEXT で持つ。**`@mba/db` はその中身の形を知らない**（`@mba/sprite` に依存しない）。
入力を `Skin` にするのは API の `parseSkin()` で、DB 層は渡された文字列をしまうだけ。
行を作る関数（`skinRow()`）が受け取るのは `parseSkin()` が返した値だけで、ほかの `Skin` は型で断る。
行の型を `SkinRow` と呼んで `Skin` と区別しているのも同じ理由（下の「型はどこに置くか」）。

### 見た目

**持つのはレシピで、絵ではない。** `skin_id` が着ているスキン、`part_overrides` が「このスロットは別のスキンのものを使う」
（スロット → スキンの id）、`colour_overrides` が「この色を、この色で着る」（`{ id, hex }` の並び）。
形式の定義と検証は [docs/02](02-sprite-format.md) §見た目のレシピ。

**組み上げた絵は、どこにも保存しない。** 名前の挙がったスキンを取ってきて 1 体に組むのは、描く側の仕事
（`@mba/sprite` の `composeAppearance()`）。保存すると、絵がユーザーの数だけ増える。色違いを 10 人が着ても、
増えるのは 10 行のレシピで、スキンは 1 つのまま。

**最初の設計で「バリアント」と呼んでいたものは、「別のスキンの同じスロット」になった。** スキンは
スロットごとにパーツを 1 つしか持たないので、差し替える先は別のスキンしかない。スキンの規格（docs/02）が
全スキンで共通だから、どのスキンのパーツを持ってきても位置が合う。

**`skin_id` は外部キー。2 つの上書きの列は JSON で、中の id は外部キーではない。** `@mba/db` は、スキンと同じく
この中身の形を知らない。書き込む前に API が確かめる（スキンは着られるか、色の id はその見た目に本当にあるか）。
スキンは消せないし書き換えられないが、retire はされうる。そのときは読む側が受け止める（下の「削除しない」）。

**行が無いプレイヤーは、既定のスキンを着ている。** `saves` と同じで、取得層（`apps/api/src/appearance.ts`）が
1 箇所で決める。聞かれただけでは行を作らない。既定のスキン（`player-default`）はモンスターの絵と同じく
所有者なしで種まきするが、こちらは「無ければ入れる」。関連テーブルを持たないので、行単位の種まきで困らない。

**着られるのは、存在するスキン全部。** 自分で描いたもの、最初からあるもの、モンスターの絵。
`GET /api/skins` は全員に同じ一覧を返すが、誰のものかは「自分のか、そうでないか」に落としてから返す。
ほかのユーザーの id はサーバの外に出ない。

### マップ

**タイル ID は種類の名前そのもの**（`"path"` / `"grass"` / `"tree"` / `"water"`）。数値にしていない。
数値は `TILE_KINDS` の並びと組でしか意味を持たず、並びを入れ替えた瞬間に保存済みのマップが黙って別物になる。
名前ならそれ自体が意味を持つ。マップはマスターデータで数も少ないので、バイト数より読みやすさを取った
（スキンのセルは逆で、数が多いから番号とランレングスにしている）。

**`tiles` は行ごとの配列ではなく、平らな配列**（`width × height` 個、左上から右へ、上から下へ）。
行の配列だと「行ごとに長さが違うマップ」が書けてしまう。`width` を 1 回だけ持つ形なら、そういうマップは表現できない。
代わりに、座標から添字を出すときの範囲チェックが要る（`x = width` が次の行の先頭を指してしまう）。
これは `@mba/core` の `tileAt()` 1 箇所に閉じ込めてある。

**歩けるかどうかは保存しない。** タイルの種類から `@mba/core` の `isWalkable()` が導く。
マップ側に「この木は通れる」と書ける場所を作ると、そのための規則が別に要るようになる。

**`spawn_x` / `spawn_y` は、セーブが無いプレイヤーの開始位置。** 必ず歩けるタイルを指す。

**出口は、乗るタイルが主キー**（`map_exits`）。1 つのタイルに出口は 1 つまでで、それをテーブルの形で言ってある。
出口は片道で、行って戻れる道は、両方のマップに 1 つずつ置いた 2 つの出口。着いたタイルが出口でも、
乗り直すまで何も起きない。

**出口は、いつも立てるタイルに着く。** 出口を保存するときに行き先のタイルを確かめ、行き先のマップを描き直すときに、
入ってくる出口が塞がらないかを確かめる（docs/04）。開始位置と同じで、「立てない場所に置かれたプレイヤー」を
読む側に考えさせないため。こちらは retire 済みのマップからの出口も数える。そうしておくと、そのマップを戻すときに
確かめ直さなくて済む。

**最初のマップに出口は種まきしない。** マップ同士をつなぐのは管理画面の仕事で、つなぐまで、最初のマップが世界の全部。

**最初のマップは API の起動時に種まきする**（`apps/api/src/maps.ts` の `ensureStarterMap()`）。
管理画面（Step 5）ができるまでマップを作る手段が無いため。行が無いときだけ入れ、あれば触らない。
管理画面で編集した後は DB の行が正本で、コード内の絵は出発点でしかない。

### モンスターとバトル

**バトルの状態はサーバにだけある。** `battles.state` に、両者の HP・能力値・技・ターン数を JSON で持つ。
ブラウザに渡すのはその一部（名前・HP・自分の技）だけで、状態を送り返させることはしない。
`status` は `state` の中の 1 項目を列に写したもの。「進行中のバトル」を SQL で聞けるようにするための重複。

**バトルがどの段階かは、型にも出る。** `state` の中の `status`（`ongoing` / `won` / `lost`）は、`@mba/core` では
型の一部（`Battle<S>`）。技を出す関数（`playTurn()`）が受け取るのは続いているバトルだけ、清算する関数（`settle()`）が
受け取るのは終わったバトルだけ。保存してあるバトルはどの段階でもありうるので、読んだ側が `status` を 1 回見てから渡す。
見ずに渡すと、実行時に断られるのではなく、コンパイルが通らない。

**バトルは始まった時点の能力値を写して持つ。** `state` の中身は種族への参照ではなく値のコピーなので、
バトルの途中でマスターデータが編集されても、そのバトルは始まったときの数字で最後まで進む。

**所持モンスターが持つのは `exp` と `damage` の 2 つの数。`level` と `hp` の列は無い。** `exp` は手に入れた
経験値、`damage` は減ったままの HP。画面に出るレベルと HP は、読むたびに導く（`@mba/core` の `grown()`）。
レベルは経験値から。HP は、そのレベルでの最大 HP から `damage` を引いたもの。歩けるかどうかをタイルの種類から
導くのと同じで、導けるものは保存しない。最初の計画では `level` / `exp` / `hp` の 3 列だった。

この向きで持つと、3 つのことが検査なしで成り立つ。

- **0 が両方で意味を持つ。** 何も手に入れておらず、何も失っていない。列を足すとき、既にいる行に何も
  決めてやらなくてよい。`hp` を持つ形だと、既にいる行の値は種族の最大 HP を見ないと決まらない
- **レベルと経験値が食い違わない。HP が最大値を超えない。** 食い違える 2 つ目の値がそもそも無い。
  下の「型はどこに置くか」が予告していた 2 つの制約は、検査ではなく導き方で成り立つ
- **最大 HP が変わっても、保存した値が嘘にならない。** レベルが上がると最大 HP が増え、HP も同じだけ増える。
  管理者が種族の最大 HP を直しても、`damage` はそのまま意味を持つ。直した結果、最大 HP が `damage` を下回ったら、
  読むところで HP 1 として立たせる（下の「プレイヤーのデータは、取得層で受け止める」）

**成長の式はコードにある**（`expToReach()` / `levelOf()` / `statAt()`）。作者がデプロイで変えるもので、
管理画面で変えるものではない。変えれば全てのモンスターに一度に効く。導いた値をどこにも保存していないので、
直して回る行が無い。種族の `max_hp` / `attack` / `defense` は、レベル 1 のときの値という意味になった。

**バトルは、どのモンスターのものかを持つ**（`battles.monster_id`）。バトルが残すもの（経験値と、減った HP）は、
終わったときにそのモンスターへ書く。書く先は、始まったときに決まる。

**1 体のモンスターが同時に入れるバトルは 1 つ。それをテーブルの形で言う。** `monster_id` に、`status` が
`ongoing` の行だけを対象にしたユニークインデックスを張ってある。HP を持ち越すなら要る決まりで、無ければ、
無傷のうちにバトルをいくつも始めておけば、どれも無傷から戦える。アプリの検査ではなくインデックスにしたのは、
誰が行を書いても成り立たせるため。`status` を列に写しておいたのは、これを SQL で言うためだった。
終わったバトルは縛らない。1 体が戦った数だけ溜まる。

**決まりを後から足すときは、既にある行がどうなるかを先に決める。** この Step で足したのは列が 3 つと、
インデックスが 1 つ。どれも、既にある行を書き換えずに済む形にした。

| 足したもの | 既にある行は |
|---|---|
| `owned_monsters.exp` / `damage` | 既定値の 0。レベル 1 で、無傷 |
| `battles.monster_id` | NULL。この列ができる前のバトルで、何も書き戻さずに終わる |
| 進行中に限ったユニークインデックス | 掛からない。`monster_id` が NULL の行同士は、重複と見なされない |

`battles.state` の中に足した項目（戦う側の `level`）だけは、こうはいかない。JSON の中身に既定値は付けられないので、
読むところで補う（docs/04）。

**`map_encounters.weight` は確率ではなく重み。** 合計が 100 である必要が無いので、マップに種族を 1 つ足すとき
ほかの行を直さなくてよい。抽選は `@mba/core` の `pickWeighted()` で、乱数は引数で受け取る。

**`maps` に `encounter_rate` は足していない。** バトルは「草むらで調べる」という操作で始まる形にしたので、
「歩くたびに何 % で出るか」を持つ場所が要らなくなった。歩数で抽選するなら 1 歩ごとにサーバへ知らせる必要があり、
docs/04 に書いた位置の検査の線引きも引き直しになる。そこまでやる理由ができたら足す。

**草むらかどうかは保存しない。** 歩けるかどうかと同じで、タイルの種類から `@mba/core` の `hasWildMonsters()` が導く。

**モンスターの絵は、プレイヤーが描くスキンと同じテーブルに、所有者なしで入る。** 種まきの絵も
`parseSkin()` を通してから保存するので、運営のスキンだけ検証を抜ける経路は無い。行にする関数が
`Parsed<Skin>` しか受け取らないので、通さずに保存する種まきは書けない。

**最初の一式は、種族が 1 件も無いときにだけ種まきする**（`apps/api/src/seed.ts`）。1 行ずつ「無ければ入れる」に
しないのは、関連テーブルのため。管理画面で種族から技を外しても、行単位の種まきは次の起動で元に戻してしまう。

**終わったバトルも、途中で離れたバトルも、行は残る。** 消す処理は書いていない（下の「削除しない」）。

## マイグレーション

`schema.ts` を変えたら、コンテナ内で SQL を生成する。

```sh
docker compose exec dev pnpm --filter @mba/db run db:generate --name <内容を表す名前>
```

- **`--name` を必ず付ける。** 省くと drizzle-kit がランダムな名前を付けるが、その語彙には
  既存作品のキャラクター名が含まれている。public リポジトリに固有名詞を持ち込まない、というルールに触れる。
- **適用されるのは API の起動時だけ。** `runMigrations()` が `drizzle/*.sql` をファイル名順に 1 回ずつ流す。
  開発サーバ（`tsx watch`）は `.sql` を監視していないので、生成した後は API を再起動する
  （`docker compose restart dev`）。
- **適用済みのファイルは書き換えない。** 適用したかどうかはファイル名で記録しているので、
  中身を直しても二度と流れない。変更は新しいマイグレーションとして足す。
- **`drizzle/` は整形の対象から外してある**（`packages/db/.prettierignore`）。drizzle-kit が生成のたびに
  書き直すファイルなので、整形すると毎回差分が出る。

## 削除しない

**マスターもスキンも物理削除しない。** セーブデータ・見た目・所持モンスターが参照しているため。
消す代わりに retire する。行はそのまま残し、`retired_at` に時刻を入れる（`species`・`moves`・`maps`・`skins` の 4 つ）。

**retire は「これから出さない」。** 一覧や選択肢から外れる。すでに持っている・使っているものは、できるかぎり
今までどおり動く。`retired_at` を消せば元に戻る。規則は `apps/api/src/retirement.ts` に 1 箇所。

### 参照は 2 種類あり、扱いが違う

| 誰からの参照か | 例 | 外そうとしたとき |
|---|---|---|
| ほかのマスター | マップ → 種族、種族 → 技、種族 → スキン、マップ → マップ（出口） | **断る**（`in_use`）。誰が使っているかを返す |
| プレイヤーのデータ | セーブ → マップ、見た目 → スキン、所持モンスター → 種族 | **断らない。** 取得層で受け止める |

分ける理由は、**誰に直せるか**。マスターからの参照は管理者が直せるので、「先にそちらを直す」と言える。
プレイヤーのデータは管理者には直せない。断ってしまうと、誰かが着ているスキンは永久に外せなくなる。

**生きているマスターは、生きているものだけを指す。** 上の「断る」を逆から言ったもので、3 つの書き込みが守る。

- **外すとき。** 生きているマスターから指されていたら断る
- **戻すとき。** retire 済みのものを指していたら断る（`depends_on_retired`）
- **保存するとき。** retire 済みのものを指す種族・マップは保存できない（`retired_skin` など）

これが守られているので、バトルや出現の抽選のような読む側は、マスター同士の参照について
「参照先が retire されていたら」を考えなくてよい。retire 済み同士は縛らない。外された種族が、外された技を
覚えたままでいるのは普通に起きる（使う側から順に外していくと、そうなる）。

### プレイヤーのデータは、取得層で受け止める

受け止める場所は、参照ごとに 1 箇所。画面は「外されたもの」を知らない。

| 参照 | 読むところ | 参照先が retire されていたら |
|---|---|---|
| セーブ → マップ | `loadSave()` | 最初のマップの開始地点を返す |
| 見た目 → スキン | `loadAppearance()` | 着ているスキンなら、既定の見た目を返す。パーツなら、そのスロットを着ているスキンのものに戻す |
| 所持モンスター → 種族 | `findSpecies()` | 何もしない。今までどおり戦える |

**行は書き換えない。** フォールバックは読むたびに決める。だから、マップやスキンを戻せば、プレイヤーは元の場所・
元の見た目に戻る。外したときに行を書き換えていたら、戻しても元には戻らない。

**retire でなく編集でも、同じ形で受け止める。** 管理者が種族の最大 HP を、あるモンスターが既に受けた `damage`
以下に下げることがある。そのモンスターの HP は、読むところ（`@mba/core` の `grown()`）が 1 として立たせる。
`damage` の行は書き換えないので、最大 HP を戻せば HP も戻る。

**取り上げない。** 外された種族のモンスターを持っているプレイヤーは、そのまま持ち続け、そのまま戦える。
retire は提示をやめることで、持ち物には触れない。

**フォールバック先そのものは外せない**（`protected`）。最初のマップと、既定のスキン。
これを外すと、ほかのものを外したときの行き先が無くなる。

### 一覧の出し方

- **管理 API の一覧は、retire 済みも返す**（`retired: true`）。見えなければ戻せない
- **プレイヤー向けの一覧は返さない。** きがえのスキンの一覧（`GET /api/skins`）に、retire 済みは出ない
- **id を知っていれば、スキンの絵は取れる**（`GET /api/skins/:id` は変えていない）。外された種族のモンスターを
  描くのに要る。外すのは提示であって、絵そのものではない
- **マップは逆で、外されたマップは `GET /api/maps/:id` でも 404。** 指しているのはセーブだけで、そのセーブは
  開始地点に戻るので、描く人がいない。プレイヤーの側がマップを読む関数（`findMap()`）が 1 つなので、そこで決めている

## 型はどこに置くか

- **DB の行の型**は Drizzle が `schema.ts` から生成する（`typeof users.$inferSelect`）
- **ドメインの型**は `@mba/core` に手で書く（`Species`, `OwnedMonster` など）

この 2 つは意図的に別物にしてある。DB の都合（NULL 許容、スネークケース、外部キー）が
ドメインの表現に染み出さないようにするため。API 層で相互に変換する。

最初は同じ形に見えるので冗長に感じるが、「レベルは 1 以上」「HP は最大値を超えない」といった
ドメインの制約を型で表そうとした瞬間に、この分離が効いてくる。

Step 12 でそのとおりになった。行（`OwnedMonsterRow`）にあるのは `exp` と `damage`。ドメインの `OwnedMonster` も
同じ 2 つを持ち、そこから `grown()` がレベルと HP を導く。画面に渡す `MonsterView` には、導いた後の値だけが入る。
3 つの形が、それぞれ別の相手（DB・規則・画面）の都合で決まっている。

Step 13 で、もう 1 つ効いた。**値がどこを通ってきたかも、型に書ける。** `parseSkin()` を通った `Skin`、
`checkSpecies()` を通った `SpeciesInput`、バトルのうち続いているもの。形は同じでも、型は別になる。
行の型とドメインの型が同じものだったら、「DB に書いてよい `Skin`」と「ただの `Skin`」を分ける場所が無かった
（[docs/04](04-api-design.md) §型だけのしるし）。
